# 화성시 버스 수요·공급 미스매칭 대시보드 — 백엔드

> 26년 여름학기 AI화성챌린지 대학생 솔루션데이 · 과제 23번(교통분야)
> 프론트엔드: [hwaseong-dashboard](https://github.com/2026-AIHwaseong-project/hwaseong-dashboard)

화성시를 1km 격자로 나눠 시간대별로 **버스 수요와 공급의 격차(MI)** 를 산출하고,
정류장·똑버스·증편을 어디에 넣을지 시뮬레이션하는 의사결정 도구의 백엔드입니다.
공공데이터로 산출한 실데이터만 씁니다.

**이 저장소가 산출 로직의 정본입니다.** 프론트는 표시만 하고, 수식·데이터 정의·검증은
여기가 기준입니다.

---

# 심사·발표용

## 1. 무엇을 하는가

버스가 부족한 곳을 승하차 실적만으로 찾으면 틀립니다. 버스가 없어서 발생하지 못한
통행은 카드에 찍히지 않기 때문입니다. 실적이 낮은 곳이 "수요가 없는 곳"인지
"버스가 없어서 못 타는 곳"인지 구분되지 않습니다.

그래서 실현수요(교통카드)와 잠재수요(거주인구)를 절반씩 섞어 수요 D 를 만들고,
운행빈도와 정류장 접근성으로 공급 S 를 만들어 같은 격자에서 표준화 차이를 봅니다.

```
공공데이터 ──00──▶ 화성시 추출 ──01/08/09/10──▶ 노선·배차·경유정류소·교통카드 OD
                                                          │
              SGIS 격자 ──02──▶ 786격자 + 읍면동          │
                                     └──────03───────────┴──▶ 격자 × 시간대 조인
                                                                      │
                                          04 ──▶ D·S·MI·4분면·우선순위 │
                                                                      │
                              05_simulate ──▶ 배치 효과·그리디 추천     │
                              05_load     ──▶ server/static/*.json ◀───┘
                              07_validate ──▶ 회귀·공간CV·정성 대조
                                                    │
                                       server/main.py (FastAPI) ──▶ 프론트
```

## 2. 산출 로직

`analysis/04_model.py` · `05_load.py` · `05_simulate.py` 기준입니다.

```
D  수요지수    = 0.5 · 정규화(승차) + 0.5 · 정규화(잠재수요)
     승차      = 교통카드 초승(환승 제외) · 평일 일평균
     잠재수요  = Σ(격자의 연령대별 거주인구 × 그 연령대의 시간대 체류비율)
                 체류비율 = 유동인구에서 구한 연령대별 시간배율
                 (03_join.py [4] — 격자마다 연령 구성이 달라 값이 다릅니다)

S  공급지수    = 0.78 · 정규화(운행빈도) + 0.22 · 정류장 커버리지
     커버리지  = clip(1 − 최근접 정류장 거리 / 600m, 0.05, 1)

MI 미스매칭    = clip( (z(D) − z(S)) × clip(D / dRef, 0, 1)^0.65 , −2.6, +2.6 )
     dRef      = D 의 55분위

need 판정      = z(D) ≥ 0.20 이고 MI ≥ 0.75

우선순위       = MI × (0.35 + 인구가중) × (1 + 1.6 · 고령인구비)
                 need 격자에만 부여하고 나머지는 0
     인구가중  = log1p(거주인구) → P3/P97 최소최대 정규화, 0~1 로 클램프

추천 배치안    = 총사업비 1원당 예상 승차 증가량(ΔB̂)이 큰 순으로
                 예산 한도까지 그리디 선택
     ΔB̂       = 포아송 회귀로 추정한 4개 시간대 합산 승차 증가량
```

**잠재수요라는 말이 두 곳에서 다른 뜻으로 쓰입니다.** 위의 D 항은 연령가중 시간배분
**인구**(`potential`)이고, KPI 로 나가는 "사각지대 잠재수요 39,110 통행/일"은 별개로
격자 인구에 `0.25`(= 전수단 통행 원단위 2.5 × 버스 분담률 0.10, 둘 다 가정계수)를
곱한 **통행량**(`flowTripsPerDay`)입니다. 0.25 는 D 계산에 쓰이지 않습니다.

정규화는 `log1p → P3/P97 최소최대`이고, 기준은 **배치 없는 상태에서 한 번만 잡고
고정**합니다. 매번 다시 잡으면 시뮬레이션 전후 KPI 를 서로 다른 자로 재게 됩니다.

**감쇠항 `(D/dRef)^0.65` 가 왜 붙는가.** 없으면 사람이 살지 않는 임야가 "공급 0"
이라는 이유만으로 최우선 사각지대로 올라옵니다. 수요가 기준점보다 낮은 격자는
격차를 그만큼 깎아, 실제로 사람이 있는 곳이 위로 오게 합니다. 클램프(±2.6)는
극단값 하나가 색 스케일 전체를 눌러버리는 것을 막습니다.
클램프 전 값은 `mi_naive`(감쇠 없음)와 함께 산출물에 남겨 비교할 수 있습니다.

**우선순위의 `0.35` 오프셋**은 인구가중이 0~1 로 정규화돼 있어서 필요합니다.
없으면 인구 하위 격자의 점수가 0 으로 눌려 순위가 인구수만 따라갑니다.
need 판정에는 클램프된 MI 를, 점수 계산에는 클램프 전 값을 씁니다.

### 수단은 겹치지 않게 정합니다

이 구분이 없으면 가장 싼 정류장이 아무 데나 선택됩니다.
지도의 수단 배지와 추천 결과가 같은 기준을 씁니다.

| 정류장 커버리지 | 진단 | 수단 | 단가 |
|---|---|---|---|
| ≥ 0.50 (정류장 300m 이내) | 정류장은 도보권 안, 버스가 뜸함 | 배차 증편 `ADD_FREQ` | 9,500만 원/년 |
| 0.15 ~ 0.50 (300~510m) | 노선은 인근인데 정류장이 멀다 | 정류장 신설 `NEW_STOP` | 4,200만 원 |
| < 0.15 (510m 초과) | 노선망 자체가 닿지 않음 | 똑버스 `DRT` | 1.8억 원/년 |

정류장 4,200만 원은 1회성 시설비(내용연수 10년, 연환산 420만 원)이고 나머지 둘은
연간 운영비입니다. 기본 예산 한도는 30억 원입니다.

**추천의 비교는 총사업비 기준입니다** — 예산 한도를 총액으로 자르므로 순위도 같은 자로
매겨야 하기 때문입니다(`server/main.py` 의 `eff = ΔB̂ / COST_KRW[mode]`). 응답에
`costCompareBasis: "total"` 로 실려 나가고, "똑버스·증편은 이듬해에도 같은 예산이 필요하다"는
단서가 함께 붙습니다. 연환산으로 순위를 매기면 예산은 총액으로 자르면서 순위는 다른 자로
매기게 되어 정류장 쪽으로 편향됩니다 — 세 가지 비교 기준을 나란히 돌려 본 사후분석이 프론트 저장소 [docs/API.md](https://github.com/2026-AIHwaseong-project/hwaseong-dashboard/blob/main/docs/API.md) §2.1 에 있습니다.

단가는 실제 사업비가 확정되지 않은 **가정값**입니다. 다만 서버 응답에는 그 플래그가
없습니다 — `meta.assumptions` 에 실려 나가는 것은 `busTripRate` 와 `minFreqPerHour` 뿐이고
`meta.cost` 는 `{krw, basis, lifeYears, annualKrw}` 만 담습니다. 화면의 "가정값" 배지는
프론트 `assets/js/config.js` 의 `COST[].confirmed` 가 단독으로 켭니다.

**절대 가드.** `적정`·`공급과잉` 판정에는 시간당 운행 2.0회라는 하한을 겁니다.
z 는 시간대 안에서의 상대평가라 밤에는 자 자체가 짧아집니다. 가드가 없으면 야간에
시간당 0.37회 다니는 향남읍 격자(인구 3,003)가 "적정"이 되고, 0.48회인 마도면이
"공급과잉"으로 찍힙니다. 실측 61곳이 이렇게 오라벨됐습니다.

### 상수는 어디서 나왔나

위 수식의 컷·임계는 전부 **1km 786격자 실데이터에서 재고 정한 값**입니다. 어림수가
아니라 측정 결과라는 뜻이고, 격자 크기를 바꾸면 값을 그대로 쓰더라도 아래 근거를
다시 재야 합니다(§9).

| 상수 | 값 | 1km 786격자에서 잰 근거 |
|---|---|---|
| 커버리지 임계 `COV_THRESHOLD_M` | 600m | 격자 중심~최근접 정류장 거리의 중앙값이 **392m**. 도보권 그대로 400m 를 쓰면 인구 > 0 격자 693칸 중 **44.9%(311칸)** 가 하한 0.05 에 깔려 접근성 차이를 못 잽니다. 600m 면 25.0%(173칸) |
| need 컷 `need_mi` | 0.75 | 0.55 로 낮추면 출근 need 가 30칸 → 48칸이 되는데 그중 **7칸이 동탄 고빈도 격자**(시간당 12.9~118.1회 운행)입니다. 출근 기준 z(D) 상한 2.55 > z(S) 상한 2.28 인 비대칭 탓이라 컷을 올려 걸러냅니다 |
| MI 감쇠 `dRef`=P55(D) · `DAMP_EXP`=0.65 | — | 인구 50 미만인 빈 땅이 **183칸**입니다. 감쇠를 거치면 그 183칸 중 need 색(MI ≥ 0.75)을 받는 칸이 **네 시간대 모두 0칸** |
| MI 클램프 `MI_CLAMP` | ±2.6 | 극단값 하나가 색 스케일을 눌러버리는 것을 막는 안전장치. 현재 분포에서는 `mi_raw` 최대가 2.216(심야)이라 **실제로 잘리는 칸은 0칸** |
| drt 게이트 `fRef` | P30(잠재수요) | 잠재수요 하위 30% 는 똑버스 후보에서 뺍니다. 빈 셀이 늘어 이 분위 기준점이 0 으로 주저앉으면 게이트가 무력화되므로 `04_model.py` 가 `fRef=0` 경고를 찍습니다 |
| need 비중 가드 | 2~25% | 현재 출근 3.8% · 낮 4.1% · 퇴근 3.7% · 심야 5.0%. 밴드를 벗어나면 `04_model.py` 가 assert 로 멈춥니다 |

수단 배지의 커버리지 컷 0.15/0.50 도 같은 자입니다 — `cov = clip(1 − 거리/600m, 0.05, 1)`
이므로 0.50 은 정류장 300m, 0.15 는 510m 과 정확히 등가입니다. 이 컷은 `04_model.py` 와
`server/main.py` 두 곳에 있어 한쪽만 고치면 지도 배지와 추천 결과가 어긋납니다.

## 3. 데이터와 시간축

### 무엇을 수요로 세는가 — 초승·평일 (2026-08-12)

| | 이전 | 이후 |
|---|---|---|
| 승차 기준 | 승차합계 (환승 포함) | **초승** — 환승 제외 |
| 일평균 기준 | 119일 통짜 평균 | **평일** 평균 |
| 일평균 승차 | 169,026 | **151,978** (−10.1%) |

**왜 환승을 빼는가.** 승차합계 2,025만 = 초승 1,650만(81.5%) + 환승 375만(18.5%)입니다.
환승은 새로 발생한 통행이 아니라 이미 버스에 탄 사람이 갈아탄 것입니다. 이걸 수요로
세면 철도 연계 격자의 D 가 통째로 부풉니다 — 환승비가 병점역후문 71.2% · 어천역 77.1% ·
야목역 81.7% 이고, 환승비 30% 이상인 66개 정류장이 전체 승차의 21.1% 를 차지합니다.

**왜 평일인가.** 주말 승차는 평일의 69.4% 이고 그 비율이 정류장마다 0.06(반월중·고등학교앞)
부터 3.59(석포산업단지)까지 약 60배 벌어집니다. 119일을 통으로 평균내면 평일 기준 대비
중앙 −10.7%(범위 −25%~+47%) 어긋납니다. 출근(07–09)·퇴근(17–19)은 통근 시간대라 평일이
맞는 자입니다. 주말분은 `board_day_we` 로 남겨 뒀습니다 — 요일축 도입 때 씁니다.

### 노선이 안 붙는 정류장이 26% 있습니다

승차량 결측 정류장 32개는 읍면동 중앙값으로 보정합니다(`03_join.py`). 운행빈도 쪽에도
같은 문제가 있습니다.

경유정류소 데이터(`route_stops_plus.csv`)는 정류장 3,158개 중 **2,320개(73.5%)** 에만
노선을 붙입니다(`09_augment_routes.py` 보강 전에는 2,201개 = 69.7% 였습니다).
나머지 838개는 노선 정보가 없어 운행빈도가 0 으로 잡히는데 실제로는 버스가 옵니다.
다만 정류장 수로는 4분의 1이어도 **승차량 비중은 2.9%** 입니다.

`routes_village.csv`(마을버스)로 메우려 했으나 **경유정류소도 좌표도 없어**
(노선번호·기점·종점·인가대수·배차뿐) 정류장에 붙일 수 없습니다.

→ `03_join.py` 는 838개 중 **승하차 실적이 있는 603개**만 같은 읍면동에서 노선이 붙은
정류장들의 중앙값으로 대체하고 `stops_hwaseong.csv` 의 `freq_imputed` 컬럼에 표시합니다.
승하차가 0 인 나머지 235개는 **일부러 대체하지 않습니다** — 진짜로 버스가 안 오는 곳이고,
여기를 채우면 찾으려던 사각지대가 사라집니다.

### 그 수요를 시간대에 어떻게 나누는가 — 교통카드 OD (2026-08-13)

원자료(정류소별 승하차)에는 시간대 정보가 없습니다. 예전에는 연령가중 유동인구
시간배율로 안분했는데, **교통카드 OD 15분단위 실측**으로 교체했습니다.

| 시간대 | 유동인구 배율 | 교통카드 OD 실측 | |
|---|---|---|---|
| 출근 07–09 | 7.7% | **18.4%** | 2.37배 과소 |
| 낮 09–17 | 43.5% | 45.1% | 1.04배 |
| 퇴근 17–19 | 10.6% | 15.3% | 1.44배 과소 |
| 심야 22–24 | 7.2% | **3.8%** | 0.53배 과대 |

두 곡선의 상관계수는 **0.42** 에 그칩니다. 유동인구 곡선은 거의 평평한데 버스 승차는
출근에 몰립니다 — 유동인구는 걷기·자가용·배달을 다 포함하기 때문입니다. 그대로 쓰면
출근 수요를 절반 이하로 깎고 심야 수요를 두 배로 부풀립니다.

곡선은 **법정동별 25개**를 씁니다(시 전체 곡선 하나가 아닙니다). 표본이 없는 동은
시 전체 곡선으로 대체합니다.

**승차량 B 에만 적용하고 잠재수요 P 는 유동인구 기준을 유지합니다.** 심야에 버스가
없으면 카드가 안 찍히므로, 실측 곡선만 쓰면 "심야에는 수요가 없다"는 순환논리에
빠집니다. 사각지대를 찾는 것이 목적이므로 잠재수요 쪽 시간축은 건드리지 않습니다.

### 정류소를 어떤 키로 잇는가 — 정류장번호 직결

출처마다 정류소 ID 체계가 다릅니다. 승하차 원본의 고유 정류소 2,879개(정류소번호 기준
2,877개)를 분모로 재면 이렇습니다.

| 매칭 방식 | 매칭률 |
|---|---|
| `stops_gg.csv` 정류소id ↔ 승하차 정류소ID | 78.2% |
| `stops_national_hwaseong.csv` 모바일단축번호 ↔ 승하차 정류소번호 | 98.5% |
| **`stops_national_hwaseong.csv` 정류장번호 ↔ 승하차 정류소ID** | **98.9%** ✅ |
| `stops_tago.csv` node_id ↔ 승하차 정류소ID | 74.7% |

**`정류장번호` ↔ `정류소ID` 로 조인합니다.** ARS(98.5%)보다 높고, 무엇보다
**ID 는 전국 유일이지만 ARS 는 시군구 안에서만 유일**합니다. 좌표 기반 공간조인
폴백은 필요하지 않았습니다.

⚠️ **`모바일단축번호` 는 `'37539.0'` 형태로 저장돼 있습니다.** 원본에 결측이 있어
pandas 가 그 컬럼을 float 로 읽는 바람에 `.0` 이 붙었습니다. 그대로 조인하면
**매칭률이 정확히 0%** 입니다(2,877개 중 0개). `.0` 을 떼고 승하차 쪽의 앞자리 0 패딩
(`'04074'`·`'04078'`)까지 함께 정규화해야 98.5% 가 나옵니다. 0% 를 보고 "ARS 로는
못 붙는다"고 결론내면 안 됩니다.

외부로 나가는 정류장 `id` 는 계약대로 `41590-{ARS}` 형식을 유지합니다
([docs/API_SPEC.md](docs/API_SPEC.md)). **조인만 정류장번호로 하고 노출 형식은 그대로**
둡니다 — 계약을 바꾸지 않으면서 매칭률과 전국 유일성을 둘 다 가져갑니다.

### 연령 14구간을 접지 않고 남겨 둔 이유

`grid_hwaseong.csv` 는 격자 인구를 `a0009 … a70p` 14구간으로 그대로 들고 있습니다.
잠재수요를 미리 계산해 한 컬럼으로 접지 않은 데는 이유가 있습니다.

유동인구 원본(`flow_hourly.csv`)이 **시군구 단위 곡선 하나**뿐이라, 격자 인구 총계에
그 배율을 그냥 곱하면 모든 격자에 같은 배수가 걸립니다. **z-score 는 공통 배수에
불변**이므로 그렇게 하면 시간대를 바꿔도 수요 z 가 한 톨도 안 움직입니다.
연령대별로 나눠 곱해야 격자마다 연령 구성이 달라 서로 다른 시간곡선이 나옵니다
(`03_join.py` [4]). 그래서 곱셈은 조인 단계에 남기고 원자료는 14구간으로 보존합니다.

효과의 크기는 작습니다 — 잠재수요 z 의 시간대 간 최대차가 격자당 최대 0.25 입니다.
그래도 0 과 0.25 는 다릅니다.

유동인구 쪽 연령 구간은 `0009 … 6569` 13개까지라 `a70p` 에 대응하는 구간이 없습니다.
`03_join.py` 가 6569 의 시간비율을 그대로 대용합니다.

### 승차 예측 회귀 · 공간 교차검증

읍면동 단위로 나눈 공간 CV 입니다(같은 동을 학습과 평가에 함께 쓰지 않습니다).

| 지표 | 값 |
|---|---|
| 공간 CV · log | **0.8521** (목표 0.6) |
| 공간 CV · raw | 0.872 |
| 학습 · log | 0.86 |
| 인구 ≥ 200 인 354격자(실측 승차의 98.0%) · 공간 CV log | **0.8081** (raw 0.8571) |
| 배차 탄력성 | **+0.5492** |

**"격자가 1km 면 너무 굵지 않나"에 대한 답.** R² 는 해상도에 딸린 값입니다 — 셀을 잘게
쪼갤수록 셀당 승차 건수가 줄어 포아송 노이즈의 비중이 커지므로, 같은 모델이라도 셀 단위
R² 는 구조적으로 내려갑니다. 해상도를 바꿔 비교할 때 같은 자로 재는 방법은 **예측을 1km
부모 격자로 합산해 다시 재는 것(집계 후 R²)** 입니다. 올바른 진술은 "해상도를 높여도 1km
집계 예측력은 유지된다" 이지, 셀 단위 R² 가 떨어졌으니 모델이 나빠졌다가 아닙니다.
위 수치는 전부 1km 786격자 기준이고, 어느 해상도에서 잰 것인지는 `validation.json` 의
`gridSizeMeters` 에 함께 기록됩니다.

같은 이유로 해상도를 바꿨을 때 확인할 것은 R² 가 아니라 **결론이 유지되는가** 입니다 —
1km 와 500m 의 우선순위 Top10 이 같은 읍면동 구성을 가리키면 "격자 크기가 결론을 만든
것이 아니다"라는 방법론 방어(MAUP)가 됩니다. 아직 만들어 두지 않은 대조표입니다.

### AI 보고서 프롬프트 — 현재 상태와 미구현 백로그

**현재 서버는 시스템 프롬프트를 쓰지 않습니다.** `server/main.py` 의 `draft_report()` 가
지시문·현황 데이터·출력 JSON 예시를 한 덩어리로 이어붙여 user 메시지 **하나**로 보냅니다.
프로바이더 3사를 같은 코드로 태우려는 선택이지만, 그 대가로 문체·근거·섹션 구성이
요청마다 흔들립니다.

아래 시스템 프롬프트는 **아직 붙이지 않은 백로그**입니다. 붙일 때는 앞부분을 고정으로
두고 그 고정된 부분에만 `cache_control` 을 겁니다. 날짜·시간대처럼 매번 바뀌는 값을
여기에 넣으면 캐시가 전부 깨집니다 — 그런 값은 user 메시지 쪽에 넣으세요.

⚠️ **Claude 에 붙일 때 파라미터 함정이 있습니다.** 현재 기본 모델은 `claude-sonnet-5`,
프리미엄이 `claude-opus-5` 인데 이 세대에서는 `temperature`·`top_p`·`top_k` 와
`thinking={"type":"enabled","budget_tokens":N}` 이 **400 오류**입니다. 사고 깊이는

- [ ] 시뮬레이션을 함께 보냈을 때 4·5장이 그 배치안 내용을 반영한다
- [ ] `tables[].rows` 의 **각 행** 길이가 `columns` 길이와 같다

### PostgreSQL 은 왜 안 쓰는가

파이프라인이 CSV·JSON 직결이고 서버는 기동 시 `server/static/` 을 메모리에 올립니다.

서버가 필요한 이유는 셋이었는데, **그중 DB 가 실제로 필요한 것은 하나뿐입니다.**

| 서버가 필요한 이유 | 서버 필요 | DB 필요 |
|---|---|---|
| AI 보고서 (API 키를 브라우저에 넣을 수 없음) | 필요 | 불필요 |
| 시뮬레이션·추천 재계산 | 필요 | 불필요 |
| 관리자 수정·실시간 | 필요 | **필요 ← 이것만** |

그 하나는 화면에 UI 도 없는 확장 요구사항입니다. DB 를 붙이면 발표장에서 컨테이너가
하나 더 뜨고 **장애 지점이 하나 늡니다.** 데이터는 786격자 × 4시간대라 통째로 메모리에
올라갑니다 — 계약 JSON 12개, 합계 4.3MB 입니다.

**`server/schema_ops.sql` 은 지운 게 아니라 남겨 뒀습니다.** 관리자 수정으로 확장할 때
`batch_*`/`admin_*`/`v_*` 소유권 분리가 그대로 필요하기 때문입니다.

| 접두사 | 소유자 | 규칙 |
|---|---|---|
| `batch_*` | 파이프라인 | 매 실행마다 REPLACE. 사람이 수정 금지 |
| `admin_*` | 서버 | append-only. 배치가 조회조차 안 함 |
| `v_*` | — | 둘을 합친 뷰. API 는 이것만 읽음 |

이 분리가 없으면 관리자 수정 기능에서 가장 흔한 사고가 납니다 — **관리자가 화요일에
수정 → 수요일 배치 재실행 → 수정 소멸, 아무도 모름.** `v_grid_metrics` 뷰가
`COALESCE(override, batch)` 로 합치므로 배치를 몇 번 돌려도 사람이 고친 값이 살아남고,
되돌리기도 DELETE 가 아니라 `revoked_at` 을 채워 이력을 남깁니다.
`admin_grid_override.reason` 이 NOT NULL 인 것도 같은 이유입니다 — "왜 모델 값을 사람이
고쳤는가"는 심사에서 반드시 나오는 질문이고, 그 답이 DB 에 있으면 강력합니다.
`analysis/schema.sql`(DuckDB) 도 같은 성격의 초기 설계 산출물입니다.

**붙일 때가 되면** `docker-compose.yml` 의 `db` 서비스 주석을 풀고
`pip install psycopg2-binary` 하면 됩니다. `05_load.py` 는 psycopg2 가 있으면
`DATABASE_URL` 로 적재를 시도하고, 없으면 `PostgreSQL 건너뜀` 을 찍고 조용히
지나갑니다 — 별도 플래그는 없습니다. 그 다음 `server/main.py` 가 JSON 대신 `v_*` 를
읽도록 바꾸면 됩니다.

인터페이스는 파일 한 층입니다 — `05_load.py` → `server/static/*.json` → FastAPI.

실측이 아닌 것은 셋입니다.

|---|---|---|

| 사업비 단가·내용연수 | **가정값** | 실제 사업비 미확정 |

**철도역 한 곳은 수기 보강입니다.** `rail_stations.csv` 5개 역 중 동탄역만 원본에
없습니다 — SRT 는 운영사가 SR 이라 코레일 데이터에 없고, GTX-A 는 도시철도 표준데이터에
아직 미반영입니다. 화성시 통행의 최대 유인 중 하나라 비워 둘 수 없어 TAGO 정류장 실측
좌표(37.1997, 127.0962)로 채웠습니다(`00_extract_hwaseong.py` [4]). 나머지 4개
역(병점·서동탄·어천·야목)은 원본 그대로입니다.

**용량 제약은 아직 안 들어가 있습니다.** 지금은 한 노선에 정류장을 몇 개 세우든 그
노선의 버스 대수가 그대로인데 공급 S 는 계속 늘어납니다. 노선별 운행대수를 알면
`효과 × 1/(1 + k·N)` 형태로 체감을 넣을 수 있는데, **그 데이터가 지금 없습니다** —
`routes.csv`(146행)·`routes_plus.csv`(206행)의 `dispatch_num`(인가대수) 컬럼은 전부
비어 있고, 인가대수가 실제로 들어 있는 것은 `routes_village.csv`(마을버스 155노선)뿐인데
그 노선들은 경유정류소가 비공개라 산출물에서 빠져 있습니다. **인가대수를 먼저 채우는
것이 이 백로그의 선행 조건입니다.**

**교통카드 OD 의 표본 한계** — 상위 25개 동의 전조합 625쌍(실데이터 479쌍)만
수집했습니다. 전수는 188×188 = 35,344쌍이라 일일 API 한도를 넘습니다. 정류장 수로는
일부지만 **승차량 기준으로는 83.3%** 를 덮습니다. 총량이 아니라 시간분포 곡선으로만
씁니다. 세부는 `dataset_hwaseong/od_meta.json`.

**격자 해상도는 1km 이고 더 잘게 쪼개지 않습니다.** SGIS 가 실측 통계를 제공하는 표준
격자는 100m·250m·500m·1km 뿐이라 1km 를 9등분한 333m 같은 크기는 애초에 표준에 없습니다.
그리고 1km 인구를 임의로 나눠 채우면 없는 정밀도를 지어내는 것이라 "실데이터만 쓴다"는
원칙을 깹니다 — 총량은 보존돼도 셀 간 분포는 가짜가 됩니다. 더 잘게 보려면 SGIS 포털에
**500m 격자 경계 + 격자 통계를 별도 신청**해 받은 실측으로 갈아끼우는 길뿐입니다
(공공데이터포털 배포판 15141768 은 파일명이 전부 `_1K` 입니다).

**그 신청은 하지 않았고 500m 전환은 실행되지 않았습니다.** 다만 `02_grid.py --size 500`
과 하류 스크립트는 이미 파라미터화돼 있어, 데이터가 도착하면 1km 와 같은 폴더 구조에
접미사만 `_500M` 으로 맞춰 두고 재실행하면 됩니다(경로 규칙은 `02_grid.py` docstring 이
정본). 단 §2 의 컷·감쇠·가드 상수는 1km 786격자 분포에서 잰 값이라, 그때는 값을 그대로
쓰더라도 근거를 전부 다시 재야 합니다.

**통신사 유동인구는 확보하지 못했습니다.** SKT 로부터 제공 불가 회신을 받아
경기도 빅데이터 분석갤러리 유동인구로 대체했습니다.

**받았지만 못 쓴 원본이 하나 있습니다.** 화성시 공간정보시스템 데이터
([15118266](https://www.data.go.kr/data/15118266/fileData.do))를 행정경계 용도로 받았는데,
열어 보니 **CSV 13개가 전부 속성 테이블뿐이고 지오메트리가 없습니다.** `도형번호` 컬럼으로
별도 도형 파일을 참조하는 구조인데 그 도형 파일이 배포본에 없습니다.

| 파일 | 왜 못 쓰나 |
|---|---|
| `BML_ADMB_AS` 행정경계 | **좌표 없음.** 행정구역명·코드만. 받은 목적이 여기였는데 실패 |
| `RDL_STAT_PS` 정류장 | 좌표 없음 · `정류장명` 이 전부 공백 → 정류장 3,158개와 조인 불가 |
| `RDL_CCTV`/`STLT`/`TFSN` 등 | CCTV·가로등·교통표지. 모델과 무관 |
| `화성시 VDS 자료.xlsx` | 좌표는 있으나(EPSG:5186) **검지기 위치만이고 교통량 값이 없음** |

행정경계는 SGIS 읍면동(`hwaseong_dong.geojson`)으로 해결했습니다.
**이 폴더는 다시 받을 필요가 없습니다.**

시뮬레이션·추천 결과는 위 가정에 기반한 정책 검토용 참고 수치이며,
실제 집행 전에는 실측 단가·현장 실사로 재검증이 필요합니다.
