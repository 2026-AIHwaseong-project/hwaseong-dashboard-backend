# 화성시 버스 수요·공급 미스매칭 대시보드 — 백엔드

> 26년 여름학기 AI화성챌린지 대학생 솔루션데이 · 과제 23번(교통분야)
> 프론트엔드: [hwaseong-dashboard](https://github.com/2026-AIHwaseong-project/hwaseong-dashboard)

화성시를 1km 격자로 나눠 시간대별로 **버스 수요와 공급의 격차(MI)** 를 산출하고,
정류장·똑버스·증편을 어디에 넣을지 시뮬레이션하는 의사결정 도구의 백엔드입니다.
공공데이터로 산출한 실데이터만 씁니다.

**분석 리포트가 아니라 행정이 클릭해서 쓰는 도구입니다.** 격자를 클릭해 정류장·똑버스·
증편을 놓아 보고, 예산 한도 안에서 무엇이 가장 효율적인지 그 자리에서 비교할 수 있어야
합니다.

**이 저장소가 산출 로직의 정본입니다.** 프론트는 표시만 하고, 수식·데이터 정의·검증은
여기가 기준입니다.

# 심사·발표용

## 1. 무엇을 하는가

### 왜 화성시인가

| 조건 | 실측 | 교통에 미치는 영향 |
|---|---|---|
| 면적 | 약 844km² · 동서 54.9km × 남북 29.9km | 노선 하나가 커버할 거리가 비정상적으로 김 |
| 인구 구조 | 1,026,706명. 동탄 신도시 ↔ 서부 농어촌 공존 | 격자당 거주인구가 병점2동 25,931명/km² ↔ 송산면 105명/km² 로 **247배** 벌어짐 |
| 도시 형태 | 도농복합 + 구도심 + 신도시 혼재 | 단일 노선 설계 원칙이 통하지 않음 |

인구 상위 50칸(전체의 6.4%)에 인구의 **63.5%** 가 몰려 있습니다. 넓은 면적과 낮은
밀집도가 겹치면 적자 노선 구조가 고착됩니다 — 그래서 "어디에나 노선을 깐다"가 아니라
**"어디에 무엇을 넣을지 고른다"** 가 문제가 됩니다.

### 무엇이 진짜 문제인가

화성시는 이미 **똑버스(수요응답형버스)** 와 **서부 행복택시** 에 예산을 쓰고 있습니다.
문제는 부족이 아니라 —

> **"다음 똑버스 한 대를, 다음 정류장 하나를 어디에 넣어야 가장 많은 사람이 혜택을
> 보는가에 대한 정량적 근거가 없다."**

이 저장소는 그 근거를 만듭니다.

버스가 부족한 곳을 승하차 실적만으로 찾으면 틀립니다. 버스가 없어서 발생하지 못한
통행은 카드에 찍히지 않기 때문입니다. 실적이 낮은 곳이 "수요가 없는 곳"인지
"버스가 없어서 못 타는 곳"인지 구분되지 않습니다.

그래서 실현수요(교통카드)와 잠재수요(거주인구)를 절반씩 섞어 수요 D 를 만들고,
운행빈도와 정류장 접근성으로 공급 S 를 만들어 같은 격자에서 표준화 차이를 봅니다.

### 누가 쓰는가

| 순위 | 사용자 | 사용 장면 | 필요한 것 |
|---|---|---|---|
| 1차 | 화성시 교통 담당 부서 | 노선 개편안·똑버스 증차 계획 수립 | 우선순위 랭킹, 근거 수치, 시뮬레이션 |
| 2차 | 시의회·예산 부서 | 예산 심의 타당성 검토 | "이 돈으로 몇 명이 혜택 보나" |
| 3차 | 시민·언론 | 우리 동네가 왜 불편한지 | 지도 한 장 |

**1차 사용자만 보고 만듭니다.** 3차까지 챙기려다 아무한테도 안 쓰이는 대시보드가 됩니다.
모바일 대응을 하지 않은 것도 이 판단에서 나옵니다 — 1차 사용자는 사무실 모니터로 봅니다.

```

                                                          │
              SGIS 격자 ──02──▶ 786격자 + 읍면동          │
                                     └──────03───────────┴──▶ 격자 × 시간대 조인
                                                                      │
                                          04 ──▶ D·S·MI·4분면·우선순위 │
                                                                      │
                              05_simulate ──▶ 배치 효과·그리디 추천     │
                              05_load     ──▶ server/static/*.json ◀───┘

                                                    │
                                       server/main.py (FastAPI) ──▶ 프론트
```

## 2. 산출 로직

`analysis/04_model.py` · `05_load.py` · `05_simulate.py` 기준입니다.

```
D  수요지수    = 0.5 · 정규화(승차) + 0.5 · 정규화(잠재수요)
     승차      = 교통카드 초승(환승 제외) · 평일 일평균
     잠재수요  = Σ(격자의 연령대별 거주인구 × 그 연령대의 시간대 체류비율)
                 체류비율 = 유동인구에서 구한 연령대별 시간배율
                 (03_join.py [4] — 격자마다 연령 구성이 달라 값이 다릅니다)

S  공급지수    = 0.78 · 정규화(운행빈도) + 0.22 · 정류장 커버리지
     커버리지  = clip(1 − 최근접 정류장 거리 / 600m, 0.05, 1)

MI 미스매칭    = clip( (z(D) − z(S)) × clip(D / dRef, 0, 1)^0.65 , −2.6, +2.6 )
     dRef      = D 의 55분위

need 판정      = z(D) ≥ 0.20 이고 MI ≥ 0.75

우선순위       = MI × (0.35 + 인구가중) × (1 + 1.6 · 고령인구비)
                 need 격자에만 부여하고 나머지는 0
     인구가중  = log1p(거주인구) → P3/P97 최소최대 정규화, 0~1 로 클램프

추천 배치안    = 총사업비 1원당 예상 승차 증가량(ΔB̂)이 큰 순으로
                 예산 한도까지 그리디 선택
     ΔB̂       = 포아송 회귀로 추정한 4개 시간대 합산 승차 증가량
```

**잠재수요라는 말이 두 곳에서 다른 뜻으로 쓰입니다.** 위의 D 항은 연령가중 시간배분
**인구**(`potential`)이고, KPI 로 나가는 "사각지대 잠재수요 39,110 통행/일"은 별개로
격자 인구에 `0.25`(= 전수단 통행 원단위 2.5 × 버스 분담률 0.10, 둘 다 가정계수)를
곱한 **통행량**(`flowTripsPerDay`)입니다. 0.25 는 D 계산에 쓰이지 않습니다.

**도보권 800m 와 커버리지 임계 600m 는 서로 다른 자입니다.** 정류장의 승하차·운행빈도를
격자에 뿌리는 **안분 반경은 800m** 이고(`03_join.py` 의 `WALK_M`, 거리 감쇠 가중
`1 − d/800`), 공급지수 S 의 **커버리지 임계는 600m** 입니다(`04_model.py` 의
`COV_THRESHOLD_M`).

⚠️ **`grid_join.csv` 에도 `coverage` 컬럼이 있지만 그건 800m 기준입니다.** `04_model.py` 가
그 컬럼을 무시하고 `nearest_stop_m` 에서 600m 로 다시 계산합니다. 산출물의 아무 `coverage`
나 읽어 수단 배지(0.15/0.50)를 검산하면 결론이 뒤집힙니다 — 예를 들어 `다사6707` 은
800m 기준 0.2649(정류장 신설 구간)지만 600m 기준으로는 0.05(똑버스 구간)입니다.
**정본은 `grid_metrics.csv` 쪽 `coverage` 입니다.**

정규화는 `log1p → P3/P97 최소최대`이고, 기준은 **배치 없는 상태에서 한 번만 잡고
고정**합니다. 매번 다시 잡으면 시뮬레이션 전후 KPI 를 서로 다른 자로 재게 됩니다.

**시뮬레이션의 배치 효과는 S 에 더해지는 제3의 항이 아닙니다.** 초기에는 수단마다
커버리지·공급에 상수를 더하는 가산 계수 방식이었는데 폐기했습니다. 지금은 운행빈도와
최근접 정류장 거리라는 물리량을 실제로 바꾼 뒤 위와 **같은 2항 식으로 S 를 다시
계산**합니다(`05_simulate.py`). 수요측은 고정하고 공급측만 다시 계산하며, 승차 증가량만
포아송 회귀 ΔB̂ 로 따로 추정합니다. 고정된 `norm_stats.json` 이 필요한 것이 이 때문입니다 —
물리량이 바뀌어도 자는 그대로여야 배치 전후가 비교됩니다.

**감쇠항 `(D/dRef)^0.65` 가 왜 붙는가.** 없으면 사람이 살지 않는 임야가 "공급 0"
이라는 이유만으로 최우선 사각지대로 올라옵니다. 수요가 기준점보다 낮은 격자는
격차를 그만큼 깎아, 실제로 사람이 있는 곳이 위로 오게 합니다. 클램프(±2.6)는
극단값 하나가 색 스케일 전체를 눌러버리는 것을 막습니다.
클램프 전 값은 `mi_naive`(감쇠 없음)와 함께 산출물에 남겨 비교할 수 있습니다.

**우선순위의 `0.35` 오프셋**은 인구가중이 0~1 로 정규화돼 있어서 필요합니다.
없으면 인구 하위 격자의 점수가 0 으로 눌려 순위가 인구수만 따라갑니다.
need 판정에는 클램프된 MI 를, 점수 계산에는 클램프 전 값을 씁니다.

**인접한 need 격자를 하나의 실행 단위로 묶는 방식을 만들어 봤다가 되돌렸습니다.**
행정 결재 단위로는 묶음이 맞지만, 묶음 이름(「동탄2 일대 Ⅱ」)만으로는 지도 어디인지 바로
안 보이고 격자 ID 가 사라져 지도·산점도·표를 오가며 같은 대상을 확인하기 어려웠습니다.
그래서 상위 10개를 격자 그대로 내보냅니다. need 격자가 시간대당 29~39개라 묶을 이유도
없습니다 — 대상이 수백 개로 늘면 그리디 확장 대신 **DBSCAN(eps = 1격자, minPts = 3)** 과
**묶음/격자 보기 토글**을 함께 두는 편이 낫습니다.

### 수단은 겹치지 않게 정합니다

이 구분이 없으면 가장 싼 정류장이 아무 데나 선택됩니다.
지도의 수단 배지와 추천 결과가 같은 기준을 씁니다.

| 정류장 커버리지 | 진단 | 수단 | 단가 |
|---|---|---|---|
| ≥ 0.50 (정류장 300m 이내) | 정류장은 도보권 안, 버스가 뜸함 | 배차 증편 `ADD_FREQ` | 9,500만 원/년 |
| 0.15 ~ 0.50 (300~510m) | 노선은 인근인데 정류장이 멀다 | 정류장 신설 `NEW_STOP` | 4,200만 원 |
| < 0.15 (510m 초과) | 노선망 자체가 닿지 않음 | 똑버스 `DRT` | 1.8억 원/년 |

정류장 4,200만 원은 1회성 시설비(내용연수 10년, 연환산 420만 원)이고 나머지 둘은
연간 운영비입니다. 기본 예산 한도는 30억 원입니다.

**사분면과 수단은 다른 축입니다.** 예전에는 수단도 사분면에서 뽑았는데, 그러면 지도가
"똑버스"라고 표시한 격자를 클릭해 추천을 돌렸을 때 신설이나 증차가 나왔습니다. 화면
배지와 추천이 같은 말을 하도록 수단은 커버리지 한쪽으로 통일했고, 사분면은 수요·공급의
위치를 나타내는 별개 축으로 남겼습니다.

그래서 둘이 어긋나 보이는 칸이 있습니다 — 심야 기준 `drt` 사분면 75칸 중 **27칸은 수단이
똑버스가 아닙니다**(신설 23 · 증차 4). 수요·공급이 둘 다 낮아도 정류장이 510m 안에 있어
노선망 자체는 닿아 있는 격자이고, 그런 곳에 먼저 필요한 것은 수요응답형이 아니라
정류장이나 배차입니다. 사분면이 `drt` 인데 배지가 `증차` 라고 뜨는 것은 오류가 아닙니다.

**추천의 비교는 총사업비 기준입니다** — 예산 한도를 총액으로 자르므로 순위도 같은 자로
매겨야 하기 때문입니다(`server/main.py` 의 `eff = ΔB̂ / COST_KRW[mode]`). 응답에
`costCompareBasis: "total"` 로 실려 나가고, "똑버스·증편은 이듬해에도 같은 예산이 필요하다"는
단서가 함께 붙습니다. 연환산으로 순위를 매기면 예산은 총액으로 자르면서 순위는 다른 자로
매기게 되어 정류장 쪽으로 편향됩니다 — 세 가지 비교 기준을 나란히 돌려 본 사후분석이 프론트 저장소 [docs/API.md](https://github.com/2026-AIHwaseong-project/hwaseong-dashboard/blob/main/docs/API.md) §2.1 에 있습니다.

**단가 근거 (2026-08-14 공개자료 대조).** 처음에는 셋 다 시연용 가정값이었는데, 공식
자료를 찾아 맞춰 보니 둘이 실측과 10% 안쪽으로 들어왔습니다.

| 수단 | 우리 단가 | 대조 근거 | 차이 |
|---|---|---|---|
| 똑버스 | 1.8억 원/년 | 경기교통공사 표준운송원가 — 경기도 '23년 526,301원/일·대(연 1억 9,210만), 수원시 '24년 560,428원(연 2억 456만) | **6~12% 낮음(보수적)** |
| 배차 증편 | 9,500만 원/년 | 화성시 마을버스 345대 연간 운송원가 322억 원 → 대당 연 9,333만 원 | **1.8%** |
| 정류장 신설 | 4,200만 원 | 정보안내기(BIT)만 공개단가 확인 — 독립형 1,600만·알뜰형 500만(서울시 '16). 승차대 구조물은 미확인 | 미확정 |

증편은 '1일 4회 증편'을 **차량 1대 추가 투입에 준하는 것**으로 보고 대조했습니다 — 첨두
시간대 증편은 그 시간에 차량·기사가 따로 붙어야 하기 때문입니다. 기존 차량의 배차 간격만
조이는 경우라면 과대 추정입니다. 똑버스가 보수적인 것은 표준운송원가에 차량 감가상각비가
들어 있는데 우리 단가는 차량 구매비를 뺐다고 적고 있어서입니다. 정류장은 승차대 구조물
단가가 지자체 설계내역서 안에만 있어 공개자료로 확인하지 못했습니다(부대공사비를 뺀
스마트쉼터가 성동구 기준 소형 6,500만·중형 1억 원 '24 이라, 4,200만 원은 그 아래 범위).

정류장이 미확정이라 화면의 "가정값" 표시는 유지됩니다. 다만 서버 응답에는 그 플래그가
없습니다 — `meta.assumptions` 에 실려 나가는 것은 `busTripRate` 와 `minFreqPerHour` 뿐이고
`meta.cost` 는 `{krw, basis, lifeYears, annualKrw}` 만 담습니다. 화면의 배지는
프론트 `assets/js/config.js` 의 `COST[].confirmed` 가 단독으로 켜고, 문구도 거기서
`confirmed:false` 인 항목 이름을 모아 만듭니다("가정값 정류장 단가 미확정").

**절대 가드.** `적정`·`공급과잉` 판정에는 시간당 운행 2.0회라는 하한을 겁니다.
z 는 시간대 안에서의 상대평가라 밤에는 자 자체가 짧아집니다. 가드가 없으면 야간에
시간당 0.37회 다니는 향남읍 격자(인구 3,003)가 "적정"이 되고, 0.48회인 마도면이
"공급과잉"으로 찍힙니다. 실측 61곳이 이렇게 오라벨됐습니다.

### 상수는 어디서 나왔나

위 수식의 컷·임계는 전부 **1km 786격자 실데이터에서 재고 정한 값**입니다. 어림수가
아니라 측정 결과라는 뜻이고, 격자 크기를 바꾸면 값을 그대로 쓰더라도 아래 근거를
다시 재야 합니다(§9).

| 상수 | 값 | 1km 786격자에서 잰 근거 |
|---|---|---|
| 커버리지 임계 `COV_THRESHOLD_M` | 600m | 격자 중심~최근접 정류장 거리의 중앙값이 **392m**. 도보권 그대로 400m 를 쓰면 인구 > 0 격자 693칸 중 **44.9%(311칸)** 가 하한 0.05 에 깔려 접근성 차이를 못 잽니다. 600m 면 25.0%(173칸) |
| need 컷 `need_mi` | 0.75 | 0.55 로 낮추면 출근 need 가 30칸 → 48칸이 되는데 그중 **7칸이 동탄 고빈도 격자**(시간당 12.9~118.1회 운행)입니다. 출근 기준 z(D) 상한 2.55 > z(S) 상한 2.28 인 비대칭 탓이라 컷을 올려 걸러냅니다 |
| MI 감쇠 `dRef`=P55(D) · `DAMP_EXP`=0.65 | — | 인구 50 미만인 빈 땅이 **183칸**입니다. 감쇠를 거치면 그 183칸 중 need 색(MI ≥ 0.75)을 받는 칸이 **네 시간대 모두 0칸** |
| MI 클램프 `MI_CLAMP` | ±2.6 | 극단값 하나가 색 스케일을 눌러버리는 것을 막는 안전장치. 현재 분포에서는 `mi_raw` 최대가 2.216(심야)이라 **실제로 잘리는 칸은 0칸** |
| drt 게이트 `fRef` | P30(잠재수요) | 잠재수요 하위 30% 는 똑버스 후보에서 뺍니다. 빈 셀이 늘어 이 분위 기준점이 0 으로 주저앉으면 게이트가 무력화되므로 `04_model.py` 가 `fRef=0` 경고를 찍습니다 |
| need 비중 가드 | 2~25% | 현재 출근 3.8% · 낮 4.1% · 퇴근 3.7% · 심야 5.0%. 밴드를 벗어나면 `04_model.py` 가 assert 로 멈춥니다 |

수단 배지의 커버리지 컷 0.15/0.50 도 같은 자입니다 — `cov = clip(1 − 거리/600m, 0.05, 1)`
이므로 0.50 은 정류장 300m, 0.15 는 510m 과 정확히 등가입니다. 이 컷은 `04_model.py` 와
`server/main.py` 두 곳에 있어 한쪽만 고치면 지도 배지와 추천 결과가 어긋납니다.

### 배치 주입량은 어디서 나왔나

"AI·DATA 과제인데 어디가 AI인가"와 "그 계수 근거가 뭐죠"는 심사에서 반드시 나옵니다.
배치 한 건이 공급을 얼마나 올리는지는 어림수가 아니라 아래에서 나온 값입니다
(`analysis/05_simulate.py`).

| 파라미터 | 값 | 근거 |
|---|---|---|
| 정류장 신설 `f*` | 출퇴근 4.8회/2h창 · 낮 8회/8h창 · 심야 0 | `routes_village.csv` 에서 **인가대수 ≥ 1 이고 배차가 기재된 마을버스 120노선의 배차 중앙값**(출퇴근 **25분** · 평일 **60분**)을 시간대 창으로 환산 |
| 똑버스 `φ` | 2.4회/2h창 (낮 9.6) | 차량 1대 1.2회/h 를 시간대 창으로 환산 |
| 증편 배수 | `headway × 0.7` (운행 ×1.43) | 증편 1회 = 배차간격 30% 단축이라는 **설계 가정** |
| 추천 순위 목적함수 ΔB̂ | — | **포아송 회귀 계수** — `log1p(운행빈도)`·커버리지 항을 786격자에서 학습. 배차 탄력성 **+0.5492**(§4) |

앞의 셋은 "한 대를 넣으면 물리적으로 몇 회가 늘어나는가"이고, **어디를 먼저 고를지를
정하는 것은 맨 아래 회귀입니다.** "왜 그 숫자인가"가 결과를 뒤집는 자리는 순위 쪽이고,
거기는 손으로 정한 값이 아니라 학습된 값입니다.

## 3. 데이터와 시간축

### 무엇을 수요로 세는가 — 초승·평일 (2026-08-12)

| | 이전 | 이후 |
|---|---|---|
| 승차 기준 | 승차합계 (환승 포함) | **초승** — 환승 제외 |
| 일평균 기준 | 119일 통짜 평균 | **평일** 평균 |
| 일평균 승차 | 169,026 | **151,978** (−10.1%) |

**왜 환승을 빼는가.** 승차합계 2,025만 = 초승 1,650만(81.5%) + 환승 375만(18.5%)입니다.
환승은 새로 발생한 통행이 아니라 이미 버스에 탄 사람이 갈아탄 것입니다. 이걸 수요로
세면 철도 연계 격자의 D 가 통째로 부풉니다 — 환승비가 병점역후문 71.2% · 어천역 77.1% ·
야목역 81.7% 이고, 환승비 30% 이상인 66개 정류장이 전체 승차의 21.1% 를 차지합니다.

**왜 평일인가.** 주말 승차는 평일의 69.4% 이고 그 비율이 정류장마다 0.06(반월중·고등학교앞)
부터 3.59(석포산업단지)까지 약 60배 벌어집니다. 119일을 통으로 평균내면 평일 기준 대비
중앙 −10.7%(범위 −25%~+47%) 어긋납니다. 출근(07–09)·퇴근(17–19)은 통근 시간대라 평일이
맞는 자입니다. 주말분은 `board_day_we` 로 남겨 뒀습니다 — 요일축 도입 때 씁니다.

### 노선이 안 붙는 정류장이 26% 있습니다

승차량 결측 정류장 32개는 읍면동 중앙값으로 보정합니다(`03_join.py`). 운행빈도 쪽에도
같은 문제가 있습니다.

경유정류소 데이터(`route_stops_plus.csv`)는 정류장 3,158개 중 **2,320개(73.5%)** 에만
노선을 붙입니다(`09_augment_routes.py` 보강 전에는 2,201개 = 69.7% 였습니다).
나머지 838개는 노선 정보가 없어 운행빈도가 0 으로 잡히는데 실제로는 버스가 옵니다.
다만 정류장 수로는 4분의 1이어도 **승차량 비중은 2.9%** 입니다.

`routes_village.csv`(마을버스)로 메우려 했으나 **경유정류소도 좌표도 없어**
(노선번호·기점·종점·인가대수·배차뿐) 정류장에 붙일 수 없습니다.

→ `03_join.py` 는 838개 중 **승하차 실적이 있는 603개**만 같은 읍면동에서 노선이 붙은
정류장들의 중앙값으로 대체하고 `stops_hwaseong.csv` 의 `freq_imputed` 컬럼에 표시합니다.
승하차가 0 인 나머지 235개는 **일부러 대체하지 않습니다** — 진짜로 버스가 안 오는 곳이고,
여기를 채우면 찾으려던 사각지대가 사라집니다.

### 그 수요를 시간대에 어떻게 나누는가 — 교통카드 OD (2026-08-13)

원자료(정류소별 승하차)에는 시간대 정보가 없습니다. 예전에는 연령가중 유동인구
시간배율로 안분했는데, **교통카드 OD 15분단위 실측**으로 교체했습니다.

| 시간대 | 유동인구 배율 | 교통카드 OD 실측 | |
|---|---|---|---|
| 출근 07–09 | 7.7% | **18.4%** | 2.37배 과소 |
| 낮 09–17 | 43.5% | 45.1% | 1.04배 |
| 퇴근 17–19 | 10.6% | 15.3% | 1.44배 과소 |
| 심야 22–24 | 7.2% | **3.8%** | 0.53배 과대 |

두 곡선의 상관계수는 **0.42** 에 그칩니다. 유동인구 곡선은 거의 평평한데 버스 승차는
출근에 몰립니다 — 유동인구는 걷기·자가용·배달을 다 포함하기 때문입니다. 그대로 쓰면
출근 수요를 절반 이하로 깎고 심야 수요를 두 배로 부풀립니다.

곡선은 시 전체 하나가 아니라 **법정동별 25개**를 씁니다. 시간 모양이 동마다 다르기
때문입니다 — 베드타운은 아침에 몰리고 도심은 하루에 퍼집니다.

| 법정동 | 출근(07–09) 비중 | 최대 시간대 |
|---|---|---|
| 새솔동 | 28.5% | 8시 |
| 청계동 | 25.1% | 8시 |
| 반송동 | 15.9% | 17시 |
| 석우동 | 12.1% | 15시 |

시 전체 곡선 하나만 쓰면 이 차이가 전부 18.5%·8시로 뭉개집니다. 정류장은 ARS번호로
법정동에 붙입니다(`dataset_hwaseong/stop_emd.csv`, 2,630행). 붙는 정류장은 일부지만
승차량 기준으로는 대부분을 덮고(§9), 나머지는 시 전체 곡선으로 떨어집니다.

**표본이 적은 동은 시 전체 곡선 쪽으로 당깁니다**(`w = n/(n+1000)`). 새솔동은 원시값이
43.9% 였지만 통행이 649건뿐이라 28.5% 로 축소됐습니다. 임계값으로 자르면 1건 차이로
곡선이 튀므로 연속적으로 섞습니다. 곡선 생성은 `analysis/od_curve.py` 한 곳에만
있습니다 — 모델(`03_join.py`)과 정류장 프로파일(`05_load.py`)이 같은 승차량 B 를 서로
다른 자로 나누면 시 전체 합이 어긋나기 때문입니다.

**승차량 B 에만 적용하고 잠재수요 P 는 유동인구 기준을 유지합니다.** 심야에 버스가
없으면 카드가 안 찍히므로, 실측 곡선만 쓰면 "심야에는 수요가 없다"는 순환논리에
빠집니다. 사각지대를 찾는 것이 목적이므로 잠재수요 쪽 시간축은 건드리지 않습니다.

### 정류소를 어떤 키로 잇는가 — 정류장번호 직결

출처마다 정류소 ID 체계가 다릅니다. 승하차 원본의 고유 정류소 2,879개(정류소번호 기준
2,877개)를 분모로 재면 이렇습니다.

| 매칭 방식 | 매칭률 |
|---|---|
| `stops_gg.csv` 정류소id ↔ 승하차 정류소ID | 78.2% |
| `stops_national_hwaseong.csv` 모바일단축번호 ↔ 승하차 정류소번호 | 98.5% |
| **`stops_national_hwaseong.csv` 정류장번호 ↔ 승하차 정류소ID** | **98.9%** ✅ |
| `stops_tago.csv` node_id ↔ 승하차 정류소ID | 74.7% |

**`정류장번호` ↔ `정류소ID` 로 조인합니다.** ARS(98.5%)보다 높고, 무엇보다
**ID 는 전국 유일이지만 ARS 는 시군구 안에서만 유일**합니다. 좌표 기반 공간조인
폴백은 필요하지 않았습니다.

⚠️ **`모바일단축번호` 는 `'37539.0'` 형태로 저장돼 있습니다.** 원본에 결측이 있어
pandas 가 그 컬럼을 float 로 읽는 바람에 `.0` 이 붙었습니다. 그대로 조인하면
**매칭률이 정확히 0%** 입니다(2,877개 중 0개). `.0` 을 떼고 승하차 쪽의 앞자리 0 패딩
(`'04074'`·`'04078'`)까지 함께 정규화해야 98.5% 가 나옵니다. 0% 를 보고 "ARS 로는
못 붙는다"고 결론내면 안 됩니다.

외부로 나가는 정류장 `id` 는 계약대로 `41590-{ARS}` 형식을 유지합니다
([docs/API_SPEC.md](docs/API_SPEC.md)). **조인만 정류장번호로 하고 노출 형식은 그대로**
둡니다 — 계약을 바꾸지 않으면서 매칭률과 전국 유일성을 둘 다 가져갑니다.

### 연령 14구간을 접지 않고 남겨 둔 이유

`grid_hwaseong.csv` 는 격자 인구를 `a0009 … a70p` 14구간으로 그대로 들고 있습니다.
잠재수요를 미리 계산해 한 컬럼으로 접지 않은 데는 이유가 있습니다.

유동인구 원본(`flow_hourly.csv`)이 **시군구 단위 곡선 하나**뿐이라, 격자 인구 총계에
그 배율을 그냥 곱하면 모든 격자에 같은 배수가 걸립니다. **z-score 는 공통 배수에
불변**이므로 그렇게 하면 시간대를 바꿔도 수요 z 가 한 톨도 안 움직입니다.
연령대별로 나눠 곱해야 격자마다 연령 구성이 달라 서로 다른 시간곡선이 나옵니다
(`03_join.py` [4]). 그래서 곱셈은 조인 단계에 남기고 원자료는 14구간으로 보존합니다.

효과의 크기는 작습니다 — 잠재수요 z 의 시간대 간 최대차가 격자당 최대 0.25 입니다.
그래도 0 과 0.25 는 다릅니다.

유동인구 쪽 연령 구간은 `0009 … 6569` 13개까지라 `a70p` 에 대응하는 구간이 없습니다.
`03_join.py` 가 6569 의 시간비율을 그대로 대용합니다.

### 시간대를 나눠야 하는 이유 — 심야에 문제의 성격이 바뀝니다

같은 지도를 시간대만 바꿔 보면 **우선순위가 뒤집힙니다.**

| 시간대 | 고수요·저공급(need) | 똑버스 후보(drt) | **공급과잉(over)** | 사각지대 잠재수요 |
|---|---|---|---|---|
| 출근 07–09 | 30개 | 72개 | 21개 | 39,110 통행/일 |
| 낮 09–17 | 32개 | 64개 | 18개 | 33,966 |
| 퇴근 17–19 | 29개 | 70개 | 23개 | 37,995 |
| **심야 22–24** | **39개** | **75개** | **1개** | 41,629 |

**진짜 반전은 심야입니다.** need 격자가 30개에서 39개로 1.3배 늘고, 동시에
**공급과잉 격자가 21개에서 1개로 사라집니다.** 낮에는 "어디는 넘치고 어디는 모자란
배분 문제"인데, 밤에는 **화성시 전체가 그냥 공급이 없는 상태**로 바뀝니다.
읍면동 순위도 바뀝니다 — 향남읍이 **출근 15위에서 심야 5위로** 올라옵니다.
산업단지 교대근무를 생각하면 이쪽이 오히려 설명이 됩니다.

**하루 평균 지도 한 장으로는 이게 안 보입니다.**

> **⚠️ 이 반전이 무엇으로 만들어지는지는 정확히 말해야 합니다.** 위 표의 시간대별
> 차이는 대부분 **배차(공급)의 시간 변화**입니다. 786격자에서 시간대 간 변동을 다시
> 재면 z(공급)의 분산이 z(수요)의 **6.5배**이고, 둘을 합한 변동 중 공급이 차지하는
> 몫이 **86.7%** 입니다.
> "밤에 버스가 끊겨 사각지대가 늘어난다"는 참이지만, "수요와 공급이 각각 시간대별로
> 달라져 미스매칭이 뒤집힌다"고 말하면 과장입니다. 질문받으면 이대로 답하세요.
>
> 수요 쪽 시간축은 근거가 둘로 나뉩니다 — 승차 B 는 교통카드 OD **법정동별 25개**
> 곡선 실측이고, 잠재수요 P 는 유동인구 **시군구 단위 곡선 하나**입니다. 즉 수요의
> 시간 변화에 공간차가 있는 쪽은 승차뿐입니다.

### 승차 예측 회귀 · 공간 교차검증

읍면동 단위로 나눈 공간 CV 입니다(같은 동을 학습과 평가에 함께 쓰지 않습니다).

| 지표 | 값 |
|---|---|
| 공간 CV · log | **0.8521** (목표 0.6) |
| 공간 CV · raw | 0.872 |
| 학습 · log | 0.86 |
| 인구 ≥ 200 인 354격자(실측 승차의 98.0%) · 공간 CV log | **0.8081** (raw 0.8571) |
| 배차 탄력성 | **+0.5492** |

**"격자가 1km 면 너무 굵지 않나"에 대한 답.** R² 는 해상도에 딸린 값입니다 — 셀을 잘게
쪼갤수록 셀당 승차 건수가 줄어 포아송 노이즈의 비중이 커지므로, 같은 모델이라도 셀 단위
R² 는 구조적으로 내려갑니다. 해상도를 바꿔 비교할 때 같은 자로 재는 방법은 **예측을 1km
부모 격자로 합산해 다시 재는 것(집계 후 R²)** 입니다. 올바른 진술은 "해상도를 높여도 1km
집계 예측력은 유지된다" 이지, 셀 단위 R² 가 떨어졌으니 모델이 나빠졌다가 아닙니다.
위 수치는 전부 1km 786격자 기준이고, 어느 해상도에서 잰 것인지는 `validation.json` 의
`gridSizeMeters` 에 함께 기록됩니다.

같은 이유로 해상도를 바꿨을 때 확인할 것은 R² 가 아니라 **결론이 유지되는가** 입니다 —
1km 와 500m 의 우선순위 Top10 이 같은 읍면동 구성을 가리키면 "격자 크기가 결론을 만든
것이 아니다"라는 방법론 방어(MAUP)가 됩니다. 아직 만들어 두지 않은 대조표입니다.

### PostgreSQL + PostGIS 로 띄우기 (선택)

**먼저: 지금 이걸 켤 필요가 있는지부터 보세요.** 기본 실행은 계약 JSON 으로 완전히
동작하고, 화면·API·시뮬레이션·AI 보고서까지 전부 같습니다. DB 가 실제로 필요한 것은
**관리자 수정·실시간** 확장 하나뿐입니다(근거는 §8). 발표·시연이 목적이면 켜지 마세요 —
컨테이너가 하나 더 뜨고 장애 지점이 하나 늘어납니다.

필요한 것은 Docker 와 psycopg2 드라이버뿐입니다. `requirements.txt` 에는
`psycopg2-binary` 가 **주석 처리돼 있어** 따로 설치해야 합니다.

```bash
# 1. DB 컨테이너를 띄웁니다. --profile db 가 없으면 안 뜹니다(기본 기동 보호)
docker compose --profile db up -d db

# 2. 드라이버 설치
pip install psycopg2-binary

# 3. 접속 주소를 정합니다 — 아래 두 방법 중 하나
export DATABASE_URL=postgresql://hw:hw_pass@localhost:5432/hwaseong   # 셸에만
#   또는 .env 에 한 줄 (96행에 주석으로 들어 있습니다 — # 만 지우면 됩니다)

# 4. 계약 JSON 을 DB 로 적재 (45MB 파이프라인을 다시 돌리지 않습니다)
python analysis/06_load_db.py

# 5. JSON 과 DB 가 같은 것을 내놓는지 확인 — 종료 코드 = 다른 항목 수
python analysis/06_verify_db.py

# 6. 서버 기동
python main.py
```

접속 정보는 `docker-compose.yml` 에 박혀 있습니다 — DB `hwaseong` · 계정 `hw` ·
비밀번호 `hw_pass` · 포트 5432 · 이미지 `postgis/postgis:16-3.4-alpine`.
개발용 기본값이므로 **외부에 노출되는 곳에서는 반드시 바꾸세요.**

#### 켜졌는지 확인하는 법

서버가 기동할 때 찍는 한 줄로 갈립니다.

| 기동 로그 | 상태 |
|---|---|
| `[server] DB 에서 로드. <run>, 관리자 수정 N건` | DB 를 읽고 있습니다 |
| `[server] 계약 JSON 에서 로드` | JSON 입니다 — `DATABASE_URL` 이 없거나 연결에 실패 |
| `[db] DATABASE_URL 연결 실패. JSON 으로 갑니다: …` | 켰다고 믿었지만 JSON 입니다 |

**연결에 실패해도 서버는 뜹니다.** `server/db.py` 가 경고를 찍고 계약 JSON 으로
내려갑니다 — 시연 중 DB 가 죽어도 화면은 삽니다. 다만 조용히 넘어가지는 않습니다.
"DB 를 켰다고 믿으면서 실제로는 JSON 을 읽는" 상태가 가장 나쁘기 때문입니다.

`06_verify_db.py` 는 8개 페이로드를 **직렬화 바이트까지** 맞춰 보고, 격자 배열 순서도
따로 확인합니다. 값이 같아도 순서가 다르면 `/api/v1/priorities` 의 동점 구간 순위가
조용히 바뀌기 때문입니다(§8).

#### 스키마와 적재 규칙

`server/schema_ops.sql` 이 **빈 볼륨으로 처음 뜰 때만** 자동 실행됩니다. 스키마를 고친
뒤에는 볼륨을 지울 필요 없이 `06_load_db.py` 가 매번 다시 걸어 줍니다(전부
`IF NOT EXISTS` / `OR REPLACE`). 만드는 것은 PostGIS 확장, `batch_*` 8개,
`admin_grid_override`, `v_grid_cell`·`v_grid_metrics`·`v_grid_override` 뷰,
그리고 확장용 `scenario`·`audit_log`·`app_user`·`rt_bus_position` 입니다.

적재는 `batch_run` 시작 → `batch_*` TRUNCATE → INSERT → PostGIS 도형 생성 →
완료까지 **한 트랜잭션**이라, 도중에 죽으면 이전 내용이 그대로 남습니다.
**`admin_*` 는 TRUNCATE 대상이 아닙니다** — 배치를 몇 번 돌려도 사람이 고친 값이
살아남아야 하기 때문이고, 이게 이 스키마의 요점입니다(§8).

#### 문제가 생기면

| 증상 | 원인과 조치 |
|---|---|
| `psycopg2 가 없습니다` | `pip install psycopg2-binary` |
| `DATABASE_URL 이 없습니다` | 3번 단계를 건너뛰었습니다. `.env` 에 적었다면 `#` 을 지웠는지 확인 |
| 연결 거부 | 컨테이너가 안 떴습니다. `--profile db` 없이 `up` 하면 `db` 는 안 뜹니다. `docker compose ps` 로 확인 |
| 적재는 됐는데 서버가 JSON 을 읽음 | 서버를 띄운 셸에 `DATABASE_URL` 이 없습니다. `06_load_db.py` 를 돌린 셸과 다른 셸이면 흔합니다 |
| `06_verify_db` 가 FAIL | 계약 JSON 을 다시 만든 뒤 적재를 안 했을 가능성. `python main.py --setup` 후 `06_load_db.py` 재실행 |
| 처음부터 다시 | `docker compose --profile db down -v` (볼륨까지 삭제) 후 1번부터 |

DB 를 끄고 원래대로 돌아가려면 `DATABASE_URL` 을 지우고 서버를 다시 띄우면 됩니다.
컨테이너는 `docker compose --profile db stop db` 로 세웁니다.

- [ ] 시뮬레이션을 함께 보냈을 때 4·5장이 그 배치안 내용을 반영한다
- [ ] `tables[].rows` 의 **각 행** 길이가 `columns` 길이와 같다

### 좌표계 — 미터 연산은 5179, 밖으로 나가는 것만 4326

공공데이터는 4326·5179·5186 이 섞여 옵니다. **로드 직후 즉시 5179(Korea 2000 / Unified CS,
미터 단위)로 통일하고, 마지막 출력에서만 4326(WGS84)으로 변환합니다.** 거리·면적 연산과
격자 생성·공간조인은 전부 5179 에서 하고, 계약 JSON 으로 나가는 좌표만 4326 입니다.

**좌표계를 안 알려주는 원본도 있습니다.** `08_fetch_geometry.py` 는 노선 경로점을
5181·2097·5186·5174·5179 다섯 후보로 각각 되돌려 보고 정류소까지의 중앙거리가 가장 짧은
것을 채택하며, 그래도 60m 를 넘으면 assert 로 멈춥니다. `05_simulate.py` 는 요청마다
pyproj 를 부르지 않으려고 lon/lat → 5179 변환을 2차 다항 회귀로 근사합니다(잔차 < 0.6m).
`08`·`09`·`10` 산출물도 커밋돼 있고, `03_join` 은 파일이 있으면 쓰고 없으면
원본 경로로 되돌아갑니다 — 이 셋을 건너뛰어도 파이프라인은 그대로 돕니다.

**`02b_split_grid.py` 는 검증용 드라이런입니다.** 1km 실측 격자를 균등 4분할한
가짜 500m 격자(형제 4칸이 전부 같은 값)라 제출·발표에 쓰면 안 됩니다 — 파이프라인·서버·

`git checkout -- dataset_hwaseong/grid_hwaseong.csv` 후 `rm -f dataset_hwaseong/grid_spec.json`

실측 500m 로 갈아끼우는 조건과 그때 다시 재야 할 것은 §9 를 보세요.

### PostgreSQL — 기본은 안 쓰고, 켤 수는 있습니다

> **설치·실행 방법은 §5 「PostgreSQL + PostGIS 로 띄우기」에 있습니다.** 이 절은
> *왜 이렇게 설계했는가*만 다룹니다.
>
> 기본 동작은 DB 를 붙이기 전과 같습니다 — `docker compose up` 도 `python main.py` 도
> 계약 JSON 으로 돕니다. `DATABASE_URL` 이 있어야만 DB(`v_*` 뷰)를 읽고, 연결에
> 실패하면 경고를 찍고 JSON 으로 내려갑니다. 아래에서 걱정한 "장애 지점이 하나
> 는다"에 대한 답이 이 폴백입니다.

파이프라인이 CSV·JSON 직결이고 서버는 기동 시 `server/static/` 을 메모리에 올립니다.

서버가 필요한 이유는 셋이었는데, **그중 DB 가 실제로 필요한 것은 하나뿐입니다.**

| 서버가 필요한 이유 | 서버 필요 | DB 필요 |
|---|---|---|
| AI 보고서 (API 키를 브라우저에 넣을 수 없음) | 필요 | 불필요 |
| 시뮬레이션·추천 재계산 | 필요 | 불필요 |
| 관리자 수정·실시간 | 필요 | **필요 ← 이것만** |

**시뮬레이션이 서버에 있는 이유는 따로 있습니다.** 초기에는 시뮬레이터가 브라우저에서
직접 재계산했고, 그래서 **같은 수식이 Python 과 JS 양쪽에 존재**했습니다. 한쪽만 고치면
지도와 시뮬레이션 결과가 오류 없이 갈라지는 구조였습니다. 서버가 생기면서 시뮬레이션·
추천이 Python 한 곳으로 모였고 목업도 없앴습니다. 대신 왕복 지연이 생겨 **클릭 응답
목표를 100ms 에서 500ms 로 완화**했습니다.

그 하나는 화면에 UI 도 없는 확장 요구사항입니다. DB 를 붙이면 발표장에서 컨테이너가
하나 더 뜨고 **장애 지점이 하나 늡니다.** 데이터는 786격자 × 4시간대라 통째로 메모리에
올라갑니다 — 계약 JSON 12개, 합계 4.3MB 입니다.

**`server/schema_ops.sql` 이 그 확장의 실체입니다.** 관리자 수정을 붙이려면
`batch_*`/`admin_*`/`v_*` 소유권 분리가 그대로 필요합니다.

| 접두사 | 소유자 | 규칙 |
|---|---|---|
| `batch_*` | 파이프라인 | 매 실행마다 REPLACE. 사람이 수정 금지 |
| `admin_*` | 서버 | append-only. 배치가 조회조차 안 함 |
| `v_*` | — | 둘을 합친 뷰. API 는 이것만 읽음 |

이 분리가 없으면 관리자 수정 기능에서 가장 흔한 사고가 납니다 — **관리자가 화요일에
수정 → 수요일 배치 재실행 → 수정 소멸, 아무도 모름.** `v_grid_metrics` 뷰가
`COALESCE(override, batch)` 로 합치므로 배치를 몇 번 돌려도 사람이 고친 값이 살아남고,
되돌리기도 DELETE 가 아니라 `revoked_at` 을 채워 이력을 남깁니다.
`admin_grid_override.reason` 이 NOT NULL 인 것도 같은 이유입니다 — "왜 모델 값을 사람이
고쳤는가"는 심사에서 반드시 나오는 질문이고, 그 답이 DB 에 있으면 강력합니다.
`analysis/schema.sql`(DuckDB) 도 같은 성격의 초기 설계 산출물입니다.

이 분리가 실제로 도는지는 확인했습니다 — override 를 넣고 **배치를 통째로 다시
적재해도**(`batch_*` TRUNCATE 후 재삽입) 뷰에서 사람이 고친 값이 그대로 나옵니다.
되돌리기는 `revoked_at` 을 채우므로 이력이 남습니다.

인터페이스는 파일 한 층입니다 — `05_load.py` → `server/static/*.json` → FastAPI.
DB 는 그 옆에 붙습니다: `server/static/*.json` → `06_load_db.py` → `v_*` → FastAPI.
**계약 JSON 이 양쪽의 유일한 원본**이라 두 경로가 갈라질 수 없고, 실제로 안 갈라지는지는
`06_verify_db.py` 가 8개 페이로드 4.1MB 를 바이트로 대조합니다.

**왜 바이트까지 보는가** — `/api/v1/priorities` 는 `priorityScore` 로 정렬하는데 Python 의
`sort` 가 안정 정렬이라 **동점 격자의 순위를 배열 순서가 가릅니다.** 값만 맞고 순서가
달라지면 우선순위 1위가 조용히 바뀝니다. 그래서 `batch_grid.ord` 로 계약 JSON 의 배열
순서를 보존하고, 통과용 문서는 `jsonb` 가 아니라 `json` 으로 둡니다(`jsonb` 는 객체
키 순서를 보존하지 않습니다).

**KPI 는 저장하지 않고 격자에서 셉니다.** 저장해 두면 관리자가 어떤 칸을 `need` 로
고쳤을 때 지도에는 붉은 칸이 하나 늘고 상단 KPI 는 그대로인 화면이 나옵니다
(실제로 그렇게 나왔습니다).

|---|---|---|

| 사업비 단가·내용연수 | **일부 확정** | 똑버스·증편은 공개자료 대조로 확인(§2 산출 로직의 '단가 근거'), 정류장 단가와 내용연수는 여전히 가정값 |

**철도역 한 곳은 수기 보강입니다.** `rail_stations.csv` 5개 역 중 동탄역만 원본에
없습니다 — SRT 는 운영사가 SR 이라 코레일 데이터에 없고, GTX-A 는 도시철도 표준데이터에
아직 미반영입니다. 화성시 통행의 최대 유인 중 하나라 비워 둘 수 없어 TAGO 정류장 실측
좌표(37.1997, 127.0962)로 채웠습니다(`00_extract_hwaseong.py` [4]). 나머지 4개
역(병점·서동탄·어천·야목)은 원본 그대로입니다.

**용량 제약은 아직 안 들어가 있습니다.** 지금은 한 노선에 정류장을 몇 개 세우든 그
노선의 버스 대수가 그대로인데 공급 S 는 계속 늘어납니다. 노선별 운행대수를 알면
`효과 × 1/(1 + k·N)` 형태로 체감을 넣을 수 있는데, **그 데이터가 지금 없습니다** —
`routes.csv`(146행)·`routes_plus.csv`(206행)의 `dispatch_num`(인가대수) 컬럼은 전부
비어 있고, 인가대수가 실제로 들어 있는 것은 `routes_village.csv`(마을버스 155노선)뿐인데
그 노선들은 경유정류소가 비공개라 산출물에서 빠져 있습니다. **인가대수를 먼저 채우는
것이 이 백로그의 선행 조건입니다.**

**교통카드 OD 의 표본 한계** — 상위 25개 동의 전조합 625쌍(실데이터 479쌍)만
수집했습니다. 전수는 188×188 = 35,344쌍이라 일일 API 한도를 넘습니다. 정류장 수로는
일부지만 **승차량 기준으로는 83.3%** 를 덮습니다. 총량이 아니라 시간분포 곡선으로만
씁니다. 세부는 `dataset_hwaseong/od_meta.json`.

표본이 하루치 한 장이라 두 가지를 따로 확인했습니다. **① 그날이 특이한 날은 아닌지** —
3/16·6/1·6/8 세 날짜의 시간곡선 상관이 **0.986~0.989** 로 사실상 같은 모양이고, 특히
3/16 은 승하차 원본 기간(2025-12~2026-03) 안이라 계절 차이도 끼지 않습니다.
**② 시외 통근이 빠져 출근 첨두가 과소평가되지 않는지** — 화성→수원 25쌍을 따로 받아
보니 출근(07–09) 비중이 **18.2%** 로 시내 18.4% 와 사실상 같았습니다. 채택본은 6/1
하루치이고 나머지 두 날짜는 대조용으로만 받았습니다(커밋하지 않았습니다).

**격자 해상도는 1km 이고 더 잘게 쪼개지 않습니다.** SGIS 가 실측 통계를 제공하는 표준
격자는 100m·250m·500m·1km 뿐이라 1km 를 9등분한 333m 같은 크기는 애초에 표준에 없습니다.
그리고 1km 인구를 임의로 나눠 채우면 없는 정밀도를 지어내는 것이라 "실데이터만 쓴다"는
원칙을 깹니다 — 총량은 보존돼도 셀 간 분포는 가짜가 됩니다. 더 잘게 보려면 SGIS 포털에
**500m 격자 경계 + 격자 통계를 별도 신청**해 받은 실측으로 갈아끼우는 길뿐입니다
(공공데이터포털 배포판 15141768 은 파일명이 전부 `_1K` 입니다).

**그 신청은 하지 않았고 500m 전환은 실행되지 않았습니다.** 다만 `02_grid.py --size 500`
과 하류 스크립트는 이미 파라미터화돼 있어, 데이터가 도착하면 1km 와 같은 폴더 구조에
접미사만 `_500M` 으로 맞춰 두고 재실행하면 됩니다(경로 규칙은 `02_grid.py` docstring 이
정본). 단 §2 의 컷·감쇠·가드 상수는 1km 786격자 분포에서 잰 값이라, 그때는 값을 그대로
쓰더라도 근거를 전부 다시 재야 합니다.

**통신사 유동인구는 확보하지 못했습니다.** SKT 로부터 제공 불가 회신을 받아
경기도 빅데이터 분석갤러리 유동인구로 대체했습니다.
잠재수요 P 를 만드는 자리를 한 블록에 격리해 둔 덕분에 소스가 빠져도 교체 지점이 한
곳입니다 — `analysis/03_join.py` 의 `[4] 잠재수요 — 연령가중 시간배율` 입니다.
해상도는 SGIS 격자에서, 시간 변화는 유동인구 CSV 에서, 총량 검증은 승하차에서 각각
가져옵니다. 통신사 데이터는 이 셋을 한 소스로 합쳐 줬을 뿐이라 셋 다 대체재가 있었고,
**모델 수식은 하나도 바뀌지 않았습니다.**

> **"통신사 데이터를 왜 안 썼나" 질문에는** — "요청했으나 제공 불가 회신을 받았습니다.
> 공공데이터만으로 완주 가능하도록 설계해 뒀고, 잠재수요 생성부를 한 블록으로 격리해
> 향후 확보 시 즉시 교체 가능합니다."

**받았지만 못 쓴 원본이 하나 있습니다.** 화성시 공간정보시스템 데이터
([15118266](https://www.data.go.kr/data/15118266/fileData.do))를 행정경계 용도로 받았는데,
열어 보니 **CSV 13개가 전부 속성 테이블뿐이고 지오메트리가 없습니다.** `도형번호` 컬럼으로
별도 도형 파일을 참조하는 구조인데 그 도형 파일이 배포본에 없습니다.

| 파일 | 왜 못 쓰나 |
|---|---|
| `BML_ADMB_AS` 행정경계 | **좌표 없음.** 행정구역명·코드만. 받은 목적이 여기였는데 실패 |
| `RDL_STAT_PS` 정류장 | 좌표 없음 · `정류장명` 이 전부 공백 → 정류장 3,158개와 조인 불가 |
| `RDL_CCTV`/`STLT`/`TFSN` 등 | CCTV·가로등·교통표지. 모델과 무관 |
| `화성시 VDS 자료.xlsx` | 좌표는 있으나(EPSG:5186) **검지기 위치만이고 교통량 값이 없음** |

행정경계는 SGIS 읍면동(`hwaseong_dong.geojson`)으로 해결했습니다.
**이 폴더는 다시 받을 필요가 없습니다.**

시뮬레이션·추천 결과는 위 가정에 기반한 정책 검토용 참고 수치이며,
실제 집행 전에는 실측 단가·현장 실사로 재검증이 필요합니다.
