## 1. 한 줄 정의

**화성시를 격자로 쪼개 시간대별로 "버스가 얼마나 필요한가"와 "실제로 얼마나 닿는가"의 격차를 지도에 띄우고, 정류장·똑버스·증편을 어디에 넣을지 클릭해서 시뮬레이션하는 의사결정 도구.**

분석 리포트가 아니라 **행정이 클릭해서 쓰는 도구**입니다. 이 구분이 이 프로젝트의 전부입니다.

## 2. 문제 정의

### 2.1 화성시가 특수한 이유

| 조건 | 내용 | 교통에 미치는 영향 |
|---|---|---|
| 면적 | 전국 기초지자체 최상위급 | 노선 하나가 커버할 거리가 비정상적으로 김 |
| 인구 구조 | 인구 100만, 동탄 신도시 ↔ 서부 농어촌 공존 | 수요 밀도가 지역별 10배 이상 차이 |
| 도시 형태 | 도농복합 + 구도심 + 신도시 혼재 | 단일 노선 설계 원칙이 통하지 않음 |
| 수송분담률 | 넓은 면적 대비 낮은 인구밀집도로 타 지자체 대비 낮음 | 적자 노선 구조 고착 |

### 2.2 진짜 문제

시는 이미 **똑버스(수요응답형버스)** 와 **서부 행복택시** 에 예산을 쓰고 있습니다. 문제는 부족이 아니라 —

> **"다음 똑버스 한 대를, 다음 정류장 하나를 어디에 넣어야 가장 많은 사람이 혜택을 보는가에 대한 정량적 근거가 없다."**

### 2.3 시간대를 나눠야 하는 이유 — 실데이터로 확인된 것

> **[2026-08-11 실데이터로 전면 교체 · 2026-08-12 수요 정의 수정]** 원래 v0.2 표는 목업
> 프로토타입 수치였고, 실데이터에서 **반전의 방향이 반대로 나왔습니다.** 목업 서술
> ("출근 13개 → 심야 11개로 감소", "향남산단 출근 3위 → 심야 탈락")을 그대로 발표하면
> 심사위원이 탭을 눌러 보는 순간 화면이 발표를 반박합니다.
> 08-12 에 수요에서 환승을 빼고 평일 기준으로 바꾸면서(README "수요 정의 변경") 수치를
> 한 번 더 갱신했습니다.

같은 지도를 시간대만 바꿔 보면 **우선순위가 뒤집힙니다.** 실측(1km 786격자):

| 시간대 | 고수요·저공급(need) | 똑버스 후보(drt) | **공급과잉(over)** | 사각지대 잠재수요 |
|---|---|---|---|---|
| 출근 07–09 | 32개 | 62개 | 21개 | 46,576 통행/일 |
| 낮 09–17 | 31개 | 62개 | 18개 | 33,896 |
| 퇴근 17–19 | 31개 | 66개 | 23개 | 43,302 |
| **심야 22–24** | **43개** | **79개** | **1개** | 40,899 |

**진짜 반전은 심야입니다.** 사각지대가 출근 대비 1.3배로 늘고, 동시에 **공급과잉 격자가
21개에서 1개로 사라집니다.** 낮에는 "어디는 넘치고 어디는 모자란 배분 문제"인데,
밤에는 **화성시 전체가 그냥 공급이 없는 상태**로 바뀝니다. 성격이 다른 문제입니다.

향남읍도 목업 서술과 반대입니다 — 우선순위 최고 순위가 **출근 13위 → 심야 5위로 올라갑니다.**
산업단지 교대근무를 생각하면 이쪽이 오히려 설명이 됩니다.

**하루 평균 지도 한 장으로는 이게 안 보입니다.** 이 반전이 발표의 핵심 장면입니다.

> **⚠️ 이 반전이 무엇으로 만들어지는지는 정확히 말해야 합니다.** 유동인구 원본
> (`flow_hourly.csv`)이 **시군구 단위 1개**라, 786격자가 전부 같은 시간 프로파일을 씁니다.
> 즉 수요의 시간 변화에는 공간차가 없고, 위 표의 시간대별 차이는 사실상 **배차(공급)의
> 시간 변화**입니다(`04_model.py` [7]: 시간대 MI 변화의 91~94%가 공급 차이).
> "밤에 버스가 끊겨 사각지대가 늘어난다"는 참이지만, "수요와 공급이 각각 시간대별로
> 달라져 미스매칭이 뒤집힌다"고 말하면 과장입니다. 질문받으면 이대로 답하세요.
>
> 반면 **요일 축은 실측이고 공간차가 큽니다** — 정류장별 주말/평일 승차비가
> 반월중·고등학교앞 0.06 부터 석포산업단지 3.59 까지 약 60배 벌어집니다.
> 시간대 축을 보완할 근거가 필요하면 이쪽이 훨씬 강합니다(`board_day_we` 에 보관됨).

## 5. 분석 모델 (프로토타입 코드와 1:1)

### 5.1 격자
- 크기: **1km × 1km** (통계청 SGIS 격자 배포판 기준 — 아래 실측 참조)
- 범위: 화성시 행정경계 내부, 인구 0 격자 제외
- 격자 수: **786개** — `02_grid.py` 실측 (면적 약 844km² 기준 예상 850개였음)

> **[실측 2026-08-07]** 공공데이터포털 SGIS 배포판(15141768)은 **1km 격자만** 제공합니다(파일명 전부 `_1K`). 500m 격자는 SGIS 포털에서 별도 신청해야 하는데, 리드타임 대비 이득이 없어 **1km로 확정**합니다.
>
> 오히려 유리합니다. 격자가 786개면 프론트 목 데이터(353개)의 2.2배 수준이라 **지금의 인라인 SVG 렌더링을 그대로 쓸 수 있고**, 버스 도보권(400~500m)과 대비해 "정류장 1~2개를 커버하는 단위"로 해석이 자연스럽습니다.
>
> **⚠️ 격자코드로 화성시를 못 고릅니다.** 코드집 `adm_grid_mapping.xlsx`는 **시도 단위 매핑만** 있습니다(18행, "경기도 → 다마·다바…"). 시군구 매핑이 없어 격자코드 문자열만으로는 화성시를 필터링할 수 없으므로, **격자 경계 shp를 화성시 행정경계로 공간조인**해서 뽑아야 합니다(`02_grid.py`).

### 5.2 수요 D

```
잠재수요 P   = 유동인구 기반          (통신사 유동인구)
실현수요 B   = 실제 승하차            (교통카드 빅데이터)
D            = 0.5 · norm(B) + 0.5 · norm(P)
```

**억압수요(suppressed demand) 개념이 이 모델의 핵심입니다.**
버스가 없으면 승하차가 적고, 승하차가 적으면 "수요가 없다"고 판정되는 순환논리에 빠집니다. 잠재수요를 절반 섞어서 이 함정을 깹니다.

목업에서는 실현수요를 `B = P × min(1, (S/0.85P)^0.6)` 로 생성했지만, **실데이터에서는 B가 관측값(승하차)이므로 이 식이 필요 없습니다.** 대신 이 식의 자리에 회귀 모델이 들어갑니다 (§10).

### 5.3 공급 S

```
S = 0.78 · norm(운행빈도) + 0.22 · 정류장 커버리지 + 배치효과
정류장 커버리지 = clamp(1 − 최근접정류장거리 / 임계거리, 0.05, 1)
```

### 5.4 미스매칭 지수 MI

```
MI = clamp( (z(D) − z(S)) × clamp(D / P55(D), 0, 1)^0.65 , −2.6, +2.6 )
```

뒤의 감쇠항이 중요합니다. **수요 자체가 미미한 격자가 상대적 공급부족만으로 새빨갛게 표시되는 것을 막습니다.** 이게 없으면 사람 없는 임야가 최우선 순위로 올라옵니다.

### 5.5 4분면 분류 → 조치

| 조건 | 분류 | 조치 |
|---|---|---|
| z(D) ≥ 0.2 **and** MI ≥ 0.55 | 고수요·저공급 | **신설**(커버리지 낮음) 또는 **증차** |
| z(D) ≤ −0.3 **and** z(S) ≥ 0.3 | 저수요·고공급 | 효율화(감차·노선 조정) |
| z(D) ≤ −0.35 **and** z(S) ≤ −0.35 **and** 유동인구 ≥ P30 | 저수요·저공급 | **DRT(똑버스)** |
| z(D) ≥ 0.25 **and** z(S) ≥ 0.25 | 적정 | — |
| 그 외 | 균형권 | — |

**DRT를 저수요·저공급에 배정한 게 이 모델의 실무적 강점입니다.** 화성시 똑버스 정책 논리와 그대로 맞아떨어집니다. 노선버스를 넣기엔 수요가 부족한 곳에 수요응답형을 넣는 것이 정확히 그 제도의 취지입니다.

### 5.6 우선순위 랭킹

```
격자 우선순위 = MI⁺ × (0.35 + 수요규모) × (1 + 1.6 · 고령인구비)
```

고수요·저공급 격자를 이 점수로 정렬해 **상위 10개 격자를 그대로** 보여줍니다.

> **인접 격자를 실행 단위로 묶는 방식을 만들어 봤다가 되돌렸습니다.** 행정 결재 단위로는 묶음이 맞지만, 실제로 써 보니 지도와 대조하기 불편했습니다 — 묶음 이름(「동탄2 일대 Ⅱ」)만으로는 지도 어디인지 바로 안 보이고, 격자 ID가 사라져 지도·산점도·표를 오가며 확인하기 어려웠습니다. 격자 단위는 어느 칸인지 즉시 보입니다.
>
> 실데이터에서 need 격자가 수백 개로 늘면 다시 필요해질 수 있습니다. 그때는 그리디 확장 대신 **DBSCAN(eps=1격자, minPts=3)** 을 쓰고, **묶음/격자 보기 토글**로 두 뷰를 함께 두는 편이 낫습니다.

### 5.7 배치 시뮬레이션

| 수단 | 파급 반경 | 효과 | 제약 |
|---|---|---|---|
| 정류장 신설 | 약 1.9km | 커버리지 +0.34(거리감쇠), 공급 +0.05 | — |
| 똑버스 배치 | 약 3.0km | 공급 +0.13(거리감쇠) | — |
| 배차 증편 | 약 2.2km | 공급 +0.20 / 인접 +0.09 | 기존 정류장 인접 격자만 |

**계수는 전부 시연용 가정값입니다.** 실데이터에서는 §10의 회귀 계수로 대체해야 하며, 이 대체가 프로젝트의 AI 파트 핵심입니다.

**정규화·z 기준통계는 배치 없는 상태에서 한 번만 계산해 고정합니다.** 매번 다시 잡으면 배치 전후를 서로 다른 자로 재게 되어 KPI 비교가 무의미해집니다. 구현 시 반드시 지켜야 하는 규칙입니다.

## 7. 시스템 아키텍처

### 결론: 백엔드 서버를 만듭니다 (v0.2에서 뒤집힘)

> **상세 설계·업무 분담은 [`BACKEND.md`](BACKEND.md) 를 보세요.** 여기서는 왜 뒤집혔는지만 적습니다.

v0.2의 결론은 "정적 JSON으로 충분, 백엔드는 순손실"이었습니다.
**프론트 스펙(`docs/API.md`)을 확인하고 뒤집혔습니다.**

| 뒤집은 근거 | 왜 브라우저로 못 하나 |
|---|---|
| **AI 보고서 생성** | 프론트에 「AI 보고서 생성」 버튼이 이미 구현돼 있습니다. **Claude API 키를 브라우저에 넣을 수 없습니다.** 이것 하나로 서버가 확정됩니다 |
| **추천 배치안** | 그리디 최적화가 시뮬레이션을 루프로 수십 번 돌립니다. 목 기준 최적화 전 49초 |
| **관리자 수정·실시간** | 확장 요구사항. 사람이 고친 값이 배치 재실행에서 살아남아야 합니다 |

**이 셋이 없었으면 v0.2 결론이 맞았습니다.** 지금은 필요합니다.

```
┌─ 배치 (오프라인, 하루 1회 또는 수동) ────────────────┐
│  dataset/ → Python 파이프라인 01~05 → DB 적재         │
│  격자 생성·공간조인 · D·S·MI · 회귀 학습               │
└──────────────────────────┬───────────────────────────┘
                           │ write (batch_*)
                           ▼
                ┌──────────────────────┐
                │  PostgreSQL + PostGIS │  단일 진실 원천
                └──┬────────────────┬───┘
             read  │                │  read/write (admin_*)
                   ▼                ▼
┌─ 온라인 (FastAPI) ──────────────────────────────────┐
│  GET  /meta /grid /priorities /stops /routes        │
│  POST /simulations      ← 서버 재계산                │
│  POST /recommendations  ← 그리디 최적화               │
│  POST /reports/draft    ← Claude API 프록시 (키 보호) │
└──────────────────────────┬──────────────────────────┘
                           │ JSON
                           ▼
        프론트 (SVG 지도 + 차트, config.js 두 줄만 수정)
```

**핵심 규칙: 배치와 온라인을 섞지 않습니다.**
격자 계산이 요청 경로에 들어가면 응답이 수십 초가 되고, 배치가 운영 테이블을 잠그면 서비스가 멎습니다.

### v0.2의 판단이 완전히 틀린 건 아닙니다

"격자 786개는 브라우저가 충분히 감당한다"는 계산은 여전히 맞습니다.
그래서 **데모 안전장치**를 둡니다 — `05_load.py` 가 DB 적재와 **동시에 정적 JSON도 떨굽니다.**

```js
const grid = await fetch("/api/v1/grid?period=am").then(r => r.json())
  .catch(() => fetch("/data/grid.json").then(r => r.json()));
```

발표장에서 DB나 네트워크가 죽어도 화면은 뜹니다. **한 줄로 발표가 안전해집니다.**

### 8.4 React를 쓸 것인가

**기본은 바닐라 유지입니다.** 현재 상태 조합(시간대 4 × 레이어 4 × 선택 × 배치 목록)이 이미 다 돌아가고 있습니다. 4주짜리 공모전에 리라이트는 순손실입니다.

**React로 갈 조건** — 아래 중 둘 이상이면 전환하세요.
- 팀에 React 능숙자가 2명 이상이다
- 화면을 3개 이상으로 늘릴 계획이다
- 컴포넌트를 다른 과제에서 재사용할 계획이다

전환한다면 Vite + React. **셋 다 지금 해당하지 않으므로 바닐라 유지입니다.**

## 10. AI·모델이 실제로 하는 일

"AI·DATA 기반 과제"이므로 어디가 AI인지 명확해야 합니다.

| # | 단계 | 방법 | 왜 필요한가 |
|---|---|---|---|
| 1 | **수요 예측 회귀** | 승하차 ~ f(유동인구, 정류장수, 운행빈도, 커버리지, 고령비) | 가중치를 손으로 정하지 않고 데이터로 학습 |
| 2 | **시뮬레이터 계수 도출** | 위 회귀의 공급 항 계수 | ★ 아래 |
| 3 | 사각지대 군집화 | DBSCAN | 임계값만으로는 산발 격자가 섞임 |
| 4 | 검증 | 홀드아웃 R², 예측 vs 실측 상관 | 모델이 맞다는 증거 |

### ★ 2번이 이 프로젝트의 진짜 AI 파트입니다

지금 시뮬레이터 계수(똑버스 +0.13 등)는 **가정값**입니다. 심사에서 "그 숫자 근거가 뭐죠"가 나오면 막힙니다.

회귀로 바꾸면 이렇게 답할 수 있습니다.

> "정류장 접근거리가 100m 줄면 승하차가 평균 몇 % 증가하는지를 화성시 전체 격자로 학습했습니다. 시뮬레이터의 계수는 그 회귀계수입니다."

**"왜 0.5인가요"라는 질문 하나에 프로젝트가 무너집니다. 학습으로 나온 값이면 그 질문 자체가 사라집니다.**

### 검증 방법
1. 정류장이 있는 격자에 한해 **예측 수요 vs 실측 승하차** 상관 (목표 R² ≥ 0.6)
2. 홀드아웃: 읍면동 하나를 학습에서 빼고 예측 오차 확인
3. **정성 검증**: 도출된 우선순위 Top 5가 실제 민원·언론에서 언급된 지역과 겹치는지 대조

3번이 발표에서 제일 강합니다. "모델이 찍은 곳이 실제로 뉴스에 나온 곳입니다"가 되니까요.

### 계약이 두 개입니다

| 사이 | 계약 | 규칙 |
|---|---|---|
| 백엔드 A ↔ B | **DB 스키마** (`server/schema_ops.sql`) | A는 `batch_*` 에 쓰고 B는 `v_*` 뷰를 읽음. 서로의 테이블을 안 건드리면 충돌 없음 |
| 백엔드 ↔ 프론트 | **`docs/API.md`** | 응답 형태는 `mock.js` 가 규격. 바꾸려면 양쪽 합의 |

**둘 다 "먼저 합의하고 더미로 시작"이 원칙입니다.** A가 Day 2에 더미 `batch_grid` 를 채우고,
프론트는 `USE_MOCK: true` 로 계속 갑니다. 그러면 셋이 완전히 병렬로 움직입니다.

## 15. 발표 스토리라인 (3분)

1. **[15초]** 화성시 지도. "면적은 전국 최상위, 인구 100만. 그런데 동탄과 서부 면지역이 같은 시입니다."
2. **[30초]** 실제 노선 이야기로 문제를 인격화. 배차가 깨지는 서부 노선.
3. **[40초]** MI 히트맵 공개. "빨간 격자가 수요 대비 공급이 부족한 곳입니다."
4. **[35초]** ★ **시간대 탭 전환.** "출근엔 사각지대가 32칸인데 심야엔 43칸으로 늘고, **공급과잉 격자는 21칸에서 1칸으로 사라집니다.** 낮에는 배분 문제였던 게 밤에는 그냥 공급이 없는 문제로 바뀝니다. 하루 평균 지도 한 장으로는 이게 안 보입니다."
5. **[45초]** 시뮬레이터 시연. 시간대를 심야로 두고 추천을 돌린다 — **출근과 다른 답이 나온다.** "똑버스는 노선 자체가 없는 구간(도보권 커버리지 0.15 미만)에만 배치됩니다. 예산 30억·균형 전략 기준 심야 1순위는 동탄6동 증편이고, 똑버스는 동탄7동·화산동 두 곳에 들어갑니다."
6. **[15초]** 마무리. "화성시는 이미 똑버스를 운영합니다. 저희는 다음 한 대를 어디에 놓을지의 근거를 만들었습니다."

4번의 반전이 있어야 심사위원이 "이거 없으면 몰랐겠네"라고 생각합니다. 없으면 예쁜 지도로 끝납니다.

> **5번 시연 전 반드시 확인** — 추천은 `period` 를 실제로 반영합니다(2026-08-11 수정).
> 출근과 심야를 나란히 눌러 배치가 달라지는 것을 리허설에서 확인하세요.
> 똑버스만 보려면 `allowedTypes: ["drt"]` 로 요청하면 됩니다.
>
> **위 4·5번의 구체적 지명·숫자는 데이터를 재산출할 때마다 바뀝니다.** 실제로 08-11 에
> 노선을 보강하자 새솔동이 need 에서 빠졌고, 08-12 에 수요 정의를 고치자 순위가 또
> 움직였습니다. 발표 직전에 `07_validate.py` 를 한 번 돌려 [3] Top5 와 대조하세요 —

## 16. 성공 지표

| 구분 | 지표 | 목표 |
|---|---|---|
| 데이터 | 정류소 ID 매칭률 | ≥ 90% (✅ **98.9% 실측 달성**) |
| 모델 | 홀드아웃 R² (승하차 예측) | ≥ 0.6 |
| 결과 | 시간대별 우선순위 묶음 수 | 시간대당 5~15건 |
| 정성 | Top 5 중 실제 민원·언론 언급 지역 | 3개 이상 일치 |
| 데모 | 시뮬레이터 클릭 → KPI 반영 | **500ms 이내** (서버 왕복 포함) |
| 데모 | 추천 배치안 산출 | **3초 이내** (국소 재계산 필수) |
| 성능 | 시간대 전환 시 지도 갱신 | 300ms 이내 |

시뮬레이터 목표가 100ms → 500ms로 완화됐습니다. **서버 왕복이 생겼기 때문이고, 그 대가로
모델 로직 이중 관리와 API 키 노출 문제가 사라졌습니다.** 500ms는 클릭 반응으로 충분합니다.
