## 0. 이 문서가 v0.1에서 바뀐 점

v0.1은 자체 프로토타입(`prototype.html`)의 갭지수 모델을 기준으로 썼습니다.
팀 프로토타입이 더 나은 모델(시간대 축 · 억압수요 · 4분면 분류)을 갖고 있어 **그쪽을 정본으로 채택**하고, 아래 세 가지를 얹은 통합본을 기준으로 다시 씁니다.

| 항목 | v0.1 (폐기) | v0.2 (현재) |
|---|---|---|

| 분류 | 임계값 하나 | **4분면 → 조치 태그(신설/증차/DRT/효율화)** |

## 1. 한 줄 정의

**화성시를 격자로 쪼개 시간대별로 "버스가 얼마나 필요한가"와 "실제로 얼마나 닿는가"의 격차를 지도에 띄우고, 정류장·똑버스·증편을 어디에 넣을지 클릭해서 시뮬레이션하는 의사결정 도구.**

분석 리포트가 아니라 **행정이 클릭해서 쓰는 도구**입니다. 이 구분이 이 프로젝트의 전부입니다.

## 2. 문제 정의

### 2.1 화성시가 특수한 이유

| 조건 | 내용 | 교통에 미치는 영향 |
|---|---|---|
| 면적 | 전국 기초지자체 최상위급 | 노선 하나가 커버할 거리가 비정상적으로 김 |
| 인구 구조 | 인구 100만, 동탄 신도시 ↔ 서부 농어촌 공존 | 수요 밀도가 지역별 10배 이상 차이 |
| 도시 형태 | 도농복합 + 구도심 + 신도시 혼재 | 단일 노선 설계 원칙이 통하지 않음 |
| 수송분담률 | 넓은 면적 대비 낮은 인구밀집도로 타 지자체 대비 낮음 | 적자 노선 구조 고착 |

### 2.2 진짜 문제

시는 이미 **똑버스(수요응답형버스)** 와 **서부 행복택시** 에 예산을 쓰고 있습니다. 문제는 부족이 아니라 —

> **"다음 똑버스 한 대를, 다음 정류장 하나를 어디에 넣어야 가장 많은 사람이 혜택을 보는가에 대한 정량적 근거가 없다."**

### 2.3 시간대를 나눠야 하는 이유 — 프로토타입에서 확인된 것

같은 지도를 시간대만 바꿔 보면 **우선순위가 뒤집힙니다.**

| 시간대 | 고수요·저공급 격자 | 최우선 조치 대상 |
|---|---|---|
| 출근 07–09 | 13개 | 동탄2 일대 · **향남산단 3위** |
| 심야 22–24 | 11개 | 동탄2 일대 · 향남산단 **탈락** |

산업단지는 출근 시간대에만 문제이고 신도시는 종일 문제입니다. **하루 평균 지도 한 장으로는 이게 안 보입니다.** 이 반전이 발표의 핵심 장면입니다.

## 5. 분석 모델 (프로토타입 코드와 1:1)

### 5.1 격자
- 크기: **1km × 1km** (통계청 SGIS 격자 배포판 기준 — 아래 실측 참조)
- 범위: 화성시 행정경계 내부, 인구 0 격자 제외
- 예상 격자 수: **약 850개** (면적 약 844km² 기준)

> **[실측 2026-08-07]** 공공데이터포털 SGIS 배포판(15141768)은 **1km 격자만** 제공합니다(파일명 전부 `_1K`). 500m 격자는 SGIS 포털에서 별도 신청해야 하는데, 리드타임 대비 이득이 없어 **1km로 확정**합니다.
>
> 오히려 유리합니다. 격자가 850개면 프론트 목 데이터(353개)의 2.4배 수준이라 **지금의 인라인 SVG 렌더링을 그대로 쓸 수 있고**, 버스 도보권(400~500m)과 대비해 "정류장 1~2개를 커버하는 단위"로 해석이 자연스럽습니다.
>
> **⚠️ 격자코드로 화성시를 못 고릅니다.** 코드집 `adm_grid_mapping.xlsx`는 **시도 단위 매핑만** 있습니다(18행, "경기도 → 다마·다바…"). 시군구 매핑이 없어 격자코드 문자열만으로는 화성시를 필터링할 수 없으므로, **격자 경계 shp를 화성시 행정경계로 공간조인**해서 뽑아야 합니다(`02_grid.py`).

### 5.2 수요 D

```
잠재수요 P   = 유동인구 기반          (통신사 유동인구)
실현수요 B   = 실제 승하차            (교통카드 빅데이터)
D            = 0.5 · norm(B) + 0.5 · norm(P)
```

**억압수요(suppressed demand) 개념이 이 모델의 핵심입니다.**
버스가 없으면 승하차가 적고, 승하차가 적으면 "수요가 없다"고 판정되는 순환논리에 빠집니다. 잠재수요를 절반 섞어서 이 함정을 깹니다.

목업에서는 실현수요를 `B = P × min(1, (S/0.85P)^0.6)` 로 생성했지만, **실데이터에서는 B가 관측값(승하차)이므로 이 식이 필요 없습니다.** 대신 이 식의 자리에 회귀 모델이 들어갑니다 (§10).

### 5.3 공급 S

```
S = 0.78 · norm(운행빈도) + 0.22 · 정류장 커버리지 + 배치효과
정류장 커버리지 = clamp(1 − 최근접정류장거리 / 임계거리, 0.05, 1)
```

### 5.4 미스매칭 지수 MI

```
MI = clamp( (z(D) − z(S)) × clamp(D / P55(D), 0, 1)^0.65 , −2.6, +2.6 )
```

뒤의 감쇠항이 중요합니다. **수요 자체가 미미한 격자가 상대적 공급부족만으로 새빨갛게 표시되는 것을 막습니다.** 이게 없으면 사람 없는 임야가 최우선 순위로 올라옵니다.

### 5.5 4분면 분류 → 조치

| 조건 | 분류 | 조치 |
|---|---|---|
| z(D) ≥ 0.2 **and** MI ≥ 0.55 | 고수요·저공급 | **신설**(커버리지 낮음) 또는 **증차** |
| z(D) ≤ −0.3 **and** z(S) ≥ 0.3 | 저수요·고공급 | 효율화(감차·노선 조정) |
| z(D) ≤ −0.35 **and** z(S) ≤ −0.35 **and** 유동인구 ≥ P30 | 저수요·저공급 | **DRT(똑버스)** |
| z(D) ≥ 0.25 **and** z(S) ≥ 0.25 | 적정 | — |
| 그 외 | 균형권 | — |

**DRT를 저수요·저공급에 배정한 게 이 모델의 실무적 강점입니다.** 화성시 똑버스 정책 논리와 그대로 맞아떨어집니다. 노선버스를 넣기엔 수요가 부족한 곳에 수요응답형을 넣는 것이 정확히 그 제도의 취지입니다.

### 5.6 우선순위 랭킹

```
격자 우선순위 = MI⁺ × (0.35 + 수요규모) × (1 + 1.6 · 고령인구비)
```

고수요·저공급 격자를 이 점수로 정렬해 **상위 10개 격자를 그대로** 보여줍니다.

> **인접 격자를 실행 단위로 묶는 방식을 만들어 봤다가 되돌렸습니다.** 행정 결재 단위로는 묶음이 맞지만, 실제로 써 보니 지도와 대조하기 불편했습니다 — 묶음 이름(「동탄2 일대 Ⅱ」)만으로는 지도 어디인지 바로 안 보이고, 격자 ID가 사라져 지도·산점도·표를 오가며 확인하기 어려웠습니다. 격자 단위는 어느 칸인지 즉시 보입니다.
>
> 실데이터에서 need 격자가 수백 개로 늘면 다시 필요해질 수 있습니다. 그때는 그리디 확장 대신 **DBSCAN(eps=1격자, minPts=3)** 을 쓰고, **묶음/격자 보기 토글**로 두 뷰를 함께 두는 편이 낫습니다.

### 5.7 배치 시뮬레이션

| 수단 | 파급 반경 | 효과 | 제약 |
|---|---|---|---|
| 정류장 신설 | 약 1.9km | 커버리지 +0.34(거리감쇠), 공급 +0.05 | — |
| 똑버스 배치 | 약 3.0km | 공급 +0.13(거리감쇠) | — |
| 배차 증편 | 약 2.2km | 공급 +0.20 / 인접 +0.09 | 기존 정류장 인접 격자만 |

**계수는 전부 시연용 가정값입니다.** 실데이터에서는 §10의 회귀 계수로 대체해야 하며, 이 대체가 프로젝트의 AI 파트 핵심입니다.

**정규화·z 기준통계는 배치 없는 상태에서 한 번만 계산해 고정합니다.** 매번 다시 잡으면 배치 전후를 서로 다른 자로 재게 되어 KPI 비교가 무의미해집니다. 구현 시 반드시 지켜야 하는 규칙입니다.

## 7. 시스템 아키텍처

### 결론: 백엔드 서버를 만들지 않습니다

```
[Python 분석 파이프라인]  ── 오프라인 배치 실행 ──┐
  공공 API/파일 수집                              │
  → 격자 생성·공간조인                            │
  → 시간대별 D·S·MI·분류·우선순위·군집 산출        │
  → 회귀 계수 학습                                │
                                                 ▼
                                    public/data/*.json (수 MB)
                                                 │
[정적 웹]  ────────────────────────────────────────┘
  MapLibre 지도 + SVG 차트
  시뮬레이터는 브라우저에서 재계산
```

**왜 백엔드가 없어도 되는가**
- 격자 3,000개 × 4시간대 × 지표 10개 ≈ **JSON 5MB 미만**. 브라우저가 한 번 받아서 들고 있으면 됩니다.
- 시뮬레이션은 격자별 거리 계산 + 가중합입니다. 3,000개 × 배치 몇 건이면 **1ms 단위**로 끝납니다. 서버 왕복이 오히려 느립니다.
- 사용자별 저장·인증이 필요 없습니다.

**언제 백엔드가 필요해지는가** (지금은 아님)
- 실시간 버스 위치를 화면에 띄워야 할 때
- 시뮬레이션 결과를 공유 URL로 저장해야 할 때
- 격자가 수만 개로 늘어 클라이언트 계산이 버거울 때

그때는 Cloudflare Workers 하나로 충분합니다. **지금 만들면 순손실입니다.**

### 8.2 좌표계 규칙 — 어기면 하루 날아갑니다

| 용도 | EPSG | 비고 |
|---|---|---|
| 거리·면적 연산, 격자 생성 | **5179** (Korea 2000 / Unified CS) | **미터 단위**. 모든 공간 연산은 여기서 |

공공데이터는 4326, 5179, 5186이 섞여 옵니다. **로드 직후 즉시 5179로 통일**하고, 마지막 출력에서만 4326으로 변환하세요.

### 8.3 지도를 MapLibre로 바꾸는 이유

> **[실측 반영] 격자가 850개로 확정되면서 성능 근거는 약해졌습니다.** SVG로 850개는 충분히 버팁니다. 그래도 MapLibre를 권하는 이유는 **실제 행정경계와 배경지도** 때문입니다 — "개략도"로는 심사에서 신뢰를 얻기 어렵고, 동탄과 서신을 같은 화면에서 보려면 팬·줌이 필요합니다. **일정이 밀리면 SVG 유지가 현실적인 폴백**입니다.
>
> **[2026-08-07 갱신] 행정경계 근거는 해소됐습니다.** 프론트가 SGIS 읍면동 실경계(4읍 9면 16동)를 SVG에 직접 적용했고 좌표계도 경위도로 통일했습니다. 남은 MapLibre 근거는 **배경지도와 팬·줌** 둘뿐이라, **SVG 유지가 폴백이 아니라 기본 선택지**가 됐습니다.

프론트 현재 상태는 **SGIS 읍면동 실경계 + 경위도 좌표 + 격자 353개**입니다. 실제로는:
- 격자가 **약 850개** → SVG도 가능하지만, 실제 좌표·경계를 쓰려면 지도 라이브러리가 편합니다.
- ~~실제 행정경계가 필요해집니다~~ → **해소됨.** 손그림 개략도가 실경계로 교체됐습니다.
- 도로 배경이 있으면 좋습니다. 다만 없어도 심사 신뢰도 문제는 사라졌습니다.
- 팬·줌이 필요합니다. 동탄과 서신을 같은 화면에서 보면 격자가 너무 작습니다.

MapLibre GL JS는 무료·토큰 불필요이고, 격자를 GeoJSON 소스로 넣고 `fill-color`를 **data-driven styling**으로 지정하면 시간대 전환이 속성 교체 한 번으로 끝납니다.

```js
// 시간대 전환이 이 한 줄로 끝납니다
map.setPaintProperty('grid', 'fill-color',
  ['interpolate', ['linear'], ['get', `mi_${period}`],
   -2.6, '#1c5cab', 0, '#e9e7e0', 2.6, '#a62b28']);
```

배경 타일은 **VWorld**(국내 지명 정확) 또는 **OSM**을 씁니다.

**단, 산점도·정류장 차트는 그대로 두세요.** 지금 코드가 잘 돌고, 차트 라이브러리를 넣으면 커스터마이징과 싸우게 됩니다.

### 02_grid.py — 격자 생성
```python
# 화성시 경계를 5179로 읽고, 500m 정방 격자를 생성해 클리핑
bounds = hwaseong.to_crs(5179).total_bounds
cells = [box(x, y, x+500, y+500)
         for x in np.arange(bounds[0], bounds[2], 500)
         for y in np.arange(bounds[1], bounds[3], 500)]
grid = gpd.GeoDataFrame(geometry=cells, crs=5179)
grid = grid[grid.intersects(hwaseong.to_crs(5179).union_all())]
```

### 03_join.py — 조인 ★ 최대 난관
**정류소 ID 체계가 출처마다 다릅니다.** GBIS 정류소ID, TAGO nodeId, 경기데이터드림 정류소번호가 서로 안 맞습니다.

```python
# 1순위: ID 직접 매칭
# 2순위(폴백): 위경도 기반 최근접 공간조인 (반경 30m)
matched = gpd.sjoin_nearest(stops_a.to_crs(5179), stops_b.to_crs(5179),
                            max_distance=30, how='left')
```
**매칭률을 반드시 로그로 찍으세요.** 90% 미만이면 그 상태로 진행하지 말고 원인을 찾아야 합니다.

승하차를 격자에 배분할 때는 거리 감쇠 가중을 씁니다.

## 10. AI·모델이 실제로 하는 일

"AI·DATA 기반 과제"이므로 어디가 AI인지 명확해야 합니다.

| # | 단계 | 방법 | 왜 필요한가 |
|---|---|---|---|
| 1 | **수요 예측 회귀** | 승하차 ~ f(유동인구, 정류장수, 운행빈도, 커버리지, 고령비) | 가중치를 손으로 정하지 않고 데이터로 학습 |
| 2 | **시뮬레이터 계수 도출** | 위 회귀의 공급 항 계수 | ★ 아래 |
| 3 | 사각지대 군집화 | DBSCAN | 임계값만으로는 산발 격자가 섞임 |
| 4 | 검증 | 홀드아웃 R², 예측 vs 실측 상관 | 모델이 맞다는 증거 |

### ★ 2번이 이 프로젝트의 진짜 AI 파트입니다

지금 시뮬레이터 계수(똑버스 +0.13 등)는 **가정값**입니다. 심사에서 "그 숫자 근거가 뭐죠"가 나오면 막힙니다.

회귀로 바꾸면 이렇게 답할 수 있습니다.

> "정류장 접근거리가 100m 줄면 승하차가 평균 몇 % 증가하는지를 화성시 전체 격자로 학습했습니다. 시뮬레이터의 계수는 그 회귀계수입니다."

**"왜 0.5인가요"라는 질문 하나에 프로젝트가 무너집니다. 학습으로 나온 값이면 그 질문 자체가 사라집니다.**

### 검증 방법
1. 정류장이 있는 격자에 한해 **예측 수요 vs 실측 승하차** 상관 (목표 R² ≥ 0.6)
2. 홀드아웃: 읍면동 하나를 학습에서 빼고 예측 오차 확인
3. **정성 검증**: 도출된 우선순위 Top 5가 실제 민원·언론에서 언급된 지역과 겹치는지 대조

3번이 발표에서 제일 강합니다. "모델이 찍은 곳이 실제로 뉴스에 나온 곳입니다"가 되니까요.

## 11. 프로토타입 → 실데이터 전환 시 바뀌는 것

| 항목 | 프로토타입 | 실제 구현 |
|---|---|---|
| 격자 | 실경계 안 353개 사각형 (목) | 실제 **1km** 격자 **약 850개** |
| 지도 | SGIS 읍면동 실경계 SVG (완료) | 동일 + (선택) 배경지도·팬줌 |
| 데이터 | 시드 고정 난수 생성 | JSON fetch |
| 수요 B | 억압수요 식으로 생성 | 교통카드 승하차 관측값 |
| 시뮬 계수 | 가정값 | 회귀계수 |
| 우선순위 | 격자 Top 10 | 동일 (need 격자가 수백 개로 늘면 DBSCAN 묶음 뷰 추가 검토) |
| 정류장 프로파일 | 가우시안 합성 | 실측 시간대별 승하차 |

**바뀌지 않는 것**: 화면 구성, 상호작용, MI 정의, 4분면 분류, 우선순위 수식, 기준통계 고정 규칙.
즉 **프론트 코드의 상당 부분이 그대로 살아갑니다.** 프로토타입이 버려지는 작업이 아닙니다.
