## 0. 세 줄 요약

1. **FastAPI + PostgreSQL/PostGIS.** 프론트가 요구한 엔드포인트 10개를 구현한다.
2. **배치(Python 파이프라인)와 온라인(API)을 분리**한다. 무거운 계산은 절대 요청 경로에 넣지 않는다.
3. **A = 데이터 파이프라인 / B = API 서버.** 인터페이스는 DB 스키마 하나뿐이다.

---

## 1. 왜 서버가 필요한가 (결론이 바뀐 이유)

초기 검토에서는 "정적 JSON + 서버 없음"이 결론이었다. 프론트 스펙을 확인하고 뒤집혔다.

| 트리거 | 근거 |
|---|---|
| **AI 보고서** | 프론트에 「AI 보고서 생성」 버튼이 이미 구현됨. Claude API 키를 브라우저에 넣을 수 없음 → **서버 필수** |
| **시뮬레이션** | `POST /simulations` 가 4개 시간대 전체 + baseline + delta 를 재계산해 돌려줘야 함 |
| **관리자 수정·실시간** | 확장 요구사항 |

**이 셋이 없었으면 서버는 만들지 않는 게 맞았다.** 지금은 필요하다.

## 2. 전체 구조

```
┌─ 배치 (오프라인, 하루 1회 또는 수동) ─────────────────┐
│  dataset/  →  Python 파이프라인 01~05  →  DB 적재      │
└───────────────────────────┬──────────────────────────┘
                            │ write (batch_*)
                            ▼
                 ┌──────────────────────┐
                 │  PostgreSQL 17       │   단일 진실 원천
                 │  + PostGIS           │
                 └──┬────────────────┬──┘
              read  │                │  read / write (admin_*)
                    ▼                ▼
┌─ 온라인 (FastAPI) ───────────────────────────────────┐
│  GET  /meta /grid /priorities /stops /routes         │
│  GET  /stops/{id}/profile                            │
│  POST /simulations          ← 서버 재계산             │
│  POST /recommendations      ← 그리디 최적화            │
│  POST /reports/draft        ← Claude API 프록시       │
│  (확장) 관리자 CRUD · 실시간 SSE                       │
└───────────────────────────┬──────────────────────────┘
                            │ JSON
                            ▼
              프론트 (config.js 두 줄만 수정)
```

**핵심 규칙: 배치와 온라인을 섞지 않는다.**
격자 계산이 API 요청 경로에 들어가면 응답이 수십 초가 되고, 배치가 운영 테이블을 잠그면 서비스가 멎는다.

## 5. DB 스키마 — 소유권 분리

> 상세 DDL: [`server/schema_ops.sql`](server/schema_ops.sql)

| 접두사 | 소유자 | 규칙 |
|---|---|---|
| `batch_*` | 파이프라인(A) | 매 실행마다 REPLACE. **사람이 수정 금지** |
| `admin_*` | 서버(B) | append-only. **배치가 조회조차 안 함** |
| `v_*` | — | 둘을 합친 뷰. **API는 이것만 읽음** |

### 왜 이렇게 나누는가

관리자 수정 기능을 넣을 때 가장 흔한 사고:

```
관리자가 화요일에 수정  →  수요일 배치 재실행  →  수정 소멸. 아무도 모름.
```

`v_grid_metrics` 뷰가 `COALESCE(override, batch)` 로 합치므로, 배치를 몇 번 돌려도 관리자 수정이 살아남는다. 되돌리기도 DELETE 가 아니라 `revoked_at` 을 채워 **이력을 남긴다.**

`admin_grid_override.reason` 은 NOT NULL 이다. "왜 모델 값을 사람이 고쳤는가"는 심사에서 반드시 나오는 질문이고, 그 답이 DB에 있으면 강력하다.

### 6.2 `POST /recommendations` — 추천 배치안 ★

> 설계 원칙: **"최적화는 알고리즘, 설명은 AI"**
> 배치 위치를 LLM에 맡기면 호출마다 답이 달라지고 근거를 댈 수 없다.
> **위치는 그리디가 정하고, LLM은 근거 문장만 다듬는다.**

```
후보 = 현재 상태에서 quad 가 need 또는 drt 인 격자
예산이 남고 최대 건수에 못 미치는 동안 반복:
    각 (후보, 수단) 조합에 대해:
        수단별 적용 제약을 통과하지 못하면 건너뜀
        효율 = 줄어든 미해결 통행량 ÷ 연간 환산 사업비
    효율 1위를 채택하고 실제로 반영 → 다음 라운드
```

목적함수 (고령 가중은 우선순위 산식과 동일 계수):

```
미해결(i) = (need 또는 drt 격자) ? 잠재통행_i × (1 + 1.6 · 고령비_i) : 0
```

**수단별 적용 제약 — `coverage` 로 배타 결정된다.** (기존 "0.5 미만이면 증편 불가"에서 3구간 배타로 바뀜)

| coverage | 수단 | 진단 |
|---|---|---|
| **≥ 0.50** | `freq` 배차 증편 | 정류장은 도보권 안에 있다. 버스가 안 온다 |
| **0.15 ~ 0.50** | `stop` 정류장 신설 | 노선은 지나는데 정류장이 멀다 |
| **< 0.15** | `drt` 똑버스 | 노선 자체가 없다. 고정노선은 비효율 |

**효율 비교는 연간 환산 비용으로 한다.** 화면 표시는 원 사업비.

| 수단 | 사업비 | 성격 | 연환산 |
|---|---|---|---|
| `stop` | 4,200만 | 1회성 시설비 (내용연수 10년) | **420만/년** |
| `drt` | 1.8억 | 연간 운영비 | 1.8억/년 |
| `freq` | 9,500만 | 연간 운영비 | 9,500만/년 |

응답에 `method` / `methodLabel` / `methodNote`, 항목별 `rationale`,
`POST /simulations` 와 같은 형식의 `simulation` 객체, 그리고 `summary.stoppedBecause`
(`budget_exhausted` | `max_reached` | `no_further_gain` | `no_candidate`) 가 들어간다.

#### ⚠️ 성능 — 전체 재계산하면 못 쓴다

그리디가 매 라운드 시뮬레이션을 다시 돌리므로 `POST /simulations` 보다 훨씬 무겁다.
**배치 효과는 S 에만 영향을 주고 정규화 기준통계는 고정이므로, 반경 안 격자만
국소 재계산해도 전체 재계산과 결과가 같다.** 프론트 목에서 **49초 → 0.2초(44배)** 로 측정됐다.
서버도 같은 최적화가 필요하다.

#### ⚠️ 정류장 편향 — 심사에서 나올 질문

목 데이터로 실행해보면 연환산 기준 정류장이 똑버스보다 **43배 싸서** 추천이 정류장으로 쏠린다.

| 조건 | 결과 |
|---|---|
| 기본값 (5건) | 정류장 5 / 똑버스 0 / 증편 0 |
| 20건까지 확대 | 정류장 17 / 똑버스 2 / 증편 1 · 예산 30억 중 11.7억(39%)만 소진 |

내용연수 나눗셈을 **정류장에만** 적용한 것이 원인이다. 똑버스도 차량 내용연수로 나누거나,
연환산을 쓰지 않고 총사업비로 비교하면 균형이 맞는다. **실데이터 적용 후 재확인하고,
어느 쪽이든 근거를 문서에 남긴다.**

## 7. 업무 분담

### 축을 "데이터 vs 서비스" 로 자른다

파이프라인 단계로 자르면(01·02 / 03·04·05) 뒷사람이 계속 기다린다.
데이터와 서비스로 자르면 **둘 다 Day 1부터 병렬**로 간다.

| | **담당 A — 데이터 파이프라인** | **담당 B — API 서버** |
|---|---|---|
| 결과물 | `batch_*` 테이블 | 엔드포인트 10개 |
| 핵심 난관 | 격자 공간조인 | 시뮬레이션·추천 재계산 |
| 언어/도구 | pandas · DuckDB · pyshp/shapely | FastAPI · SQLAlchemy |

### 담당 A — 데이터 파이프라인

| # | 산출물 | 내용 |
|---|---|---|
| A1 | `01_fetch.py` | TAGO 정류소·노선, 경기도 배차, 똑버스 경유정류소 수집 → CSV |
| A2 | `02_grid.py` ★ | ✅ **완료.** 격자 shp ↔ 화성시 경계 공간조인 → **786격자** · 읍면동 배정 |
| A3 | `03_join.py` | ARS번호 매칭(실측 99.5%), 승하차 격자 배분, 철도역 거리 |
| A4 | `04_model.py` | 수요 D · 공급 S · MI · 4분면 · 우선순위 · 회귀계수 |
| A5 | `05_load.py` | `batch_grid` / `batch_grid_metrics` 적재 + `batch_run` 기록 |
| A6 | 검증 | 예측 vs 실측 승하차 상관 (목표 R² ≥ 0.6) |

**A2가 프로젝트 전체 최대 난관.** 격자코드로 화성시를 못 고르므로(코드집에 시도 매핑만 존재) shp 공간조인이 유일한 방법이고, 좌표계 실수가 여기서 난다. **막히면 일정 전체를 다시 짜야 하는 유일한 지점.**

> **A2 참고 — 프론트가 같은 일을 이미 해뒀다.** 프론트 저장소 `tools/build-boundary.py` 가
> SGIS 읍면동 SHP(`bnd_dong_00_2025_2Q`)에서 화성시 29개(4읍 9면 16동)를 뽑아
> EPSG:5179 → 4326 변환까지 한다. **읍면동 경계는 그 스크립트를 재사용하고,
> A2는 격자 SHP ↔ 그 경계의 공간조인에만 집중하면 된다.** 시군구 코드는 SGIS 기준
> `31240` 으로, 행정표준코드 `41590` 과 다르다.

### 담당 B — API 서버

| # | 산출물 | 내용 |
|---|---|---|
| B1 | 프로젝트 셋업 | FastAPI · Docker Compose · Alembic 초기 마이그레이션 |
| B2 | `GET /meta` `/grid` `/priorities` | `v_grid_metrics` → 프론트 `cells[]` 변환 계층 |
| B3 | `GET /stops` `/routes` `/stops/{id}/profile` | |
| B4 | `POST /simulations` ★ | 배치 효과 적용 후 **4시간대 재계산**. 정규화 기준통계 고정 |
| B5 | `POST /recommendations` ★ | **v1.1 신설.** 그리디 최적화 + 국소 재계산 (§6.2) |
| B6 | `POST /reports/draft` | Claude API 프록시 (`docs/AI-REPORT.md` 규격) |
| B7 | (확장) 관리자·실시간 | `admin_*` CRUD · 인증 · SSE 워커 |

**B4·B5가 B쪽 최대 난관이고, B5는 B4 위에 얹힌다.**
B4는 프론트가 배치를 바꿀 때마다 호출하므로 응답이 빨라야 하고 `baseline` 은 항상 동일해야 한다.
B5는 그 B4를 루프 안에서 수십 번 돌리므로, **국소 재계산을 B4 단계에서 미리 설계해두면
B5는 그 위에 그리디 루프만 얹으면 된다.** B4를 전체 재계산으로 짜면 B5에서 다시 갈아엎게 된다.

### 인터페이스 — 이것만 지키면 충돌 없음

| 방향 | 계약 | 마감 |
|---|---|---|
| A → B | `batch_grid` (grid_id, geom, lon, lat, 속성) | **Day 5** |
| A → B | `batch_grid_metrics` (grid_id, period, d/s/mi/quad/priority) | Day 12 |
| A → B | `mart_norm_stats` (정규화 기준통계) | Day 12 |
| B → A | 스키마 변경 요청은 **Alembic 마이그레이션으로만** | 상시 |

## 8. ⚠️ 실측으로 확인된 제약 4가지

프론트 스펙과 어긋나므로 **프론트 담당과 협의 필요.** v1.1 기준 진행 상태를 함께 적는다.

| | 제약 | 상태 |
|---|---|---|
| ① | 격자 크기·개수 | 🟡 부분 해소 |
| ② | `stops.profile` 24시간 배열 | 🔴 미해결 |
| ③ | 시간 축이 유동인구 하나에 의존 | 🔴 설계로 우회 |
| ④ | 사업비 단가 근거 없음 | 🔴 미해결 (v1.1에서 영향 확대) |

### ① 격자 250m → 1km 🟡 부분 해소

**해소된 부분** — 프론트가 실제 SGIS 읍면동 경계를 적용하면서 좌표계가
**SVG 픽셀 → 경위도(EPSG:4326)로 통일**됐다. 격자도 실제 경계 안에만 생성되어
389개 → **353개**가 됐고, 권역이 임의 묶음이 아니라 실제 행정동이 됐다.
서버가 SVG 좌표를 계산할 필요가 없어져 **변환 계층이 통째로 사라졌다.**

**남은 부분** — `meta.grid.sizeMeters: 250` 은 그대로다.
실측: SGIS 공공데이터포털 배포판은 **1km 격자만** 제공(파일명 전부 `_1K`).
화성시 실제 격자 **786개** (`02_grid.py` 실측).

→ `sizeMeters: 1000`, `cellCount: 786` 으로 수정 요청. (`displaySizeMeters: 1500` 은 화면 표시용이라 그대로 둬도 무방)

### ② `stops.profile` 시간대별 승하차 불가 🔴

승하차 원본 컬럼 실측:
```
승하차일자 | 관할관청 | 정류소ID | 정류소번호 | 정류소명 | 승차합계 | 초승 | 환승 | 하차
```
**일자별 집계라 시간대가 없다.** 24시간 프로파일을 만들 수 없다.

→ **유동인구 CSV의 시간배율로 일 총량을 안분**하고, 응답에 `"isEstimated": true` 를 넣어 추정임을 표시한다.

⚠️ **`API.md` §3.5 응답 스펙에 `isEstimated` 필드가 없다.** 프론트에 추가를 요청해야
화면에 "추정치" 표시가 붙는다. 실측인 척 내보내면 검증 파트에서 그대로 지적당한다.

### ③ 시간 축이 유동인구 하나에 의존

승하차에 시간대가 없으므로 D 와 P 가 **같은 시간배율**을 쓰게 된다.
→ 그러면 MI 의 시간대 변화가 배율에만 좌우된다.
→ **공급 쪽에 시간대별 배차(`peekAlloc`/`nPeekAlloc`/`nightAlloc`)를 넣어** 시간대별 MI 변화가 공급 변화에서 나오게 설계한다. (경기도 API 에서 취득 확인됨)

### ④ 사업비 단가가 근거 없음 (v1.1에서 영향 확대 🔴)

`cost: { stop: 42000000, drt: 180000000, freq: 95000000 }` 는 가정값.

v1.0까지는 화면 표시용 숫자였다. **v1.1부터는 추천 알고리즘이 이 값으로 순위를 매긴다.**
가정값이 곧 정책 제안 순서가 되므로 영향이 훨씬 크다. §6.2의 정류장 편향도 여기서 나온다.

→ 화성시 예산서·유사 사업 실적으로 보정하고, 보정 전까지는 **화면과 보고서 양쪽에 가정값임을 명시.**
→ 내용연수 가정(정류장 10년)도 함께 근거를 잡는다. 지금은 정류장에만 적용돼 있다.
